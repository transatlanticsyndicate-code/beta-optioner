# ext2 — Известные баги и план исправлений

> Дата: 2026-03-26 | Версия: ext2 v1.1.0

---

## БАГ 1: Цена актива (Underlying Price) не передаётся в калькулятор

**Симптом:** В калькуляторе нет цены underlying → PL-график не считается.

**Причина:** `getUnderlyingPrice()` в `src/utils.js` ищет цену через regex в `document.title`:
```
document.title = "ESU2026 Options Chain — CME_MINI:ESU2026 — TradingView"
```
Цены в title **нет**. Реальная цена на странице в элементе:
```html
<span class="priceWrap-FNchOmZg">6,655.50USD</span>
```

**Файл:** `src/utils.js` → `getUnderlyingPrice()`

**Решение:** Искать цену в `[class*="priceWrap"]` или `[class*="price"]`, парсить число из текста типа `"6,655.50USD"`.

**Статус:** ИСПРАВЛЕН (v1.1.0) — getUnderlyingPrice() ищет в [class*="priceWrap"]

## БАГ 2: IV передаётся как Ask IV вместо чистого IV

**Симптом:** IV в калькуляторе = Ask IV (21.20%), а не чистый средний IV (21.03%).

**Причина:** В `src/parser.js` → `extractSide()`:
```javascript
iv: get('ask iv %') || get('bid iv %')
```
Берётся Ask IV или Bid IV — это НЕ средний IV.

На странице TradingView есть **центральная колонка IV** (`data-cell-part="central"`, индекс [25]) — это средний IV для страйка. Текущий парсер её **не использует**.

**Файл:** `src/parser.js` → `parseOptionRow()`

**Решение:** Извлекать IV из второй central-ячейки (индекс [25] = IV колонка рядом со Strike). Это чистый IV для данного страйка.

**Статус:** ИСПРАВЛЕН (v1.1.0) — используется central IV из td[data-cell-part="central"][1]

## БАГ 3: Volume — значение может браться неверно

**Симптом:** Volume в калькуляторе не совпадает с Volume на TradingView.

**Причина:** Volume-ячейки содержат progressbar:
```html
<td data-cell-part="call">
  <div class="container-fzyZVq6w call-fzyZVq6w right-fzyZVq6w">
    <span class="value-fzyZVq6w">6</span>
    <div class="bar-p_KG7fUb" role="progressbar" aria-valuenow="33">
      <div class="value-p_KG7fUb"></div>  <!-- ← ещё один элемент с class "value" -->
    </div>
  </div>
</td>
```

`parseCellValue()` ищет первый `<span>` — это корректно для Volume. Но если структура изменится или span будет вложен глубже — может сломаться.

**Файл:** `src/parser.js` → `parseCellValue()`

**Решение:** Уточнить селектор: `cell.querySelector('span[class*="value"]')` для более точного извлечения.

**Статус:** ВЕРИФИЦИРОВАН — Volume точно совпадает (4, 14, 3 для трёх страйков)

## БАГ 4: Bid/Ask несовпадение в калькуляторе

**Симптом:** Bid/Ask в калькуляторе не совпадают с теми, что на TradingView в момент клика.

**Анализ:**
- Storage содержит корректные bid/ask (проверено через CDP)
- `convertToCalculatorFormat()` передаёт `bid` и `ask` as-is
- Калькулятор (React) после `location.reload()` может **пересчитать** bid/ask через свой API

**Вывод:** Это поведение **калькулятора**, не ext2. При reload React берёт текущие рыночные данные, которые могли измениться за секунды между кликом и reload.

**Файл:** Не требует изменений в ext2

**Статус:** Не баг ext2, поведение калькулятора

## БАГ 5: Рассинхрон панели и калькулятора при накоплении опционов

**Симптом:**
- Добавили 2 опциона → в калькуляторе 2, в панели 1
- Или наоборот: в панели 3, в калькуляторе 4
- Опцион не всегда появляется в калькуляторе после добавления

**Возможные причины:**
1. **SW спит** — `chrome.runtime.sendMessage` не доходит до background, опцион сохраняется в storage но не инжектится в калькулятор
2. **Race condition** — быстрые клики: второй `freshFetchAndInject` перезаписывает данные первого
3. **`_injectionInProgress` блокировка** — если первый инжект ещё выполняется, второй пропускается
4. **optioner.js на калькуляторе** синхронизирует обратно устаревшие данные

**Файлы:**
- `background/calculator.js` — `freshFetchAndInject()`, `_injectionInProgress`
- `src/storage.js` — `addPosition()`
- `optioner.js` — обратная синхронизация

**Решение:**
1. Автотест: 5 тикеров × 3 опциона через CDP
2. После каждого добавления: проверить storage count vs calculator count
3. Выявить конкретный сценарий рассинхрона

**Результат автотеста (2026-03-26):**
- Добавлено 3 опциона (strikes: 6575, 6625, 6675) на одном тикере ESU2026
- Panel: 3, Calculator: 3, Storage: 3 — **синхронизация OK**
- IV передаётся корректно (central IV: 21.79, 21.24, 20.65)
- Underlying price: NONE — требует перезагрузки расширения после фикса utils.js

**Статус:** Одиночный тикер — OK. Мульти-тикер тест: требует ручного переключения между тикерами на TV.

## БАГ 6: Калькулятор не переключал тикер при смене контракта

**Симптом:** При добавлении опциона от нового тикера (TSLA → AAPL) калькулятор оставался на старом контракте. VOL и IV в калькуляторе подтягивались для неправильного тикера.

**Причина:** В `background/calculator.js` → `handleOpenOptionerTab()` при уже открытой вкладке вызывался `freshFetchAndInject` напрямую без смены URL. Калькулятор (React) читает тикер из URL-параметра `?contract=`, а не из localStorage.

**Файл:** `background/calculator.js` → `handleOpenOptionerTab()`

**Решение (v1.4.5):** При уже открытой вкладке сравниваем `contract=` в текущем URL с новым тикером. Если разные — обновляем URL через `chrome.tabs.update({ url: calcUrl })` и ждём полной загрузки через `openAndWait` перед инжектом.

**Статус:** ИСПРАВЛЕН (v1.4.5)

## БАГ 7: При смене тикера старые позиции других тикеров не очищались из мержа

**Симптом:** Добавил 1 опцион MSFT → в калькуляторе 3 (1 MSFT + 2 NVDA от предыдущей сессии).

**Причина:** `injectDataIntoCalculator` мержил новые позиции со всеми `existingOptions` из localStorage, включая позиции других тикеров.

**Файл:** `background/calculator.js` → `injectDataIntoCalculator()`

**Решение (v1.4.5):** Фильтруем `knownOptions` только по текущему тикеру перед построением `knownByKey`. Позиции других тикеров отсекаются. Сценарий с сохранёнными конфигурациями не затронут (там тикер совпадает).

**Примечание:** Финальный мерж на стороне фронтенда (`useExtensionData.js`) всё ещё добавляет "manual" позиции поверх — это отдельный баг калькулятора (см. баг-репорт для Андрея).

**Статус:** ИСПРАВЛЕН частично в ext2 (v1.4.5). Остаток — на стороне фронтенда.

## БАГ 8 (фронтенд калькулятора) — для Андрея

**Симптом:** При добавлении опциона от нового тикера калькулятор показывает позиции нового тикера + старые позиции предыдущего тикера.

**Воспроизведение:**
1. Добавить 2 опциона NVDA → калькулятор показывает 2
2. Перейти на MSFT, добавить 1 опцион → калькулятор показывает 3 (1 MSFT + 2 NVDA)

**Лог калькулятора:**
```
🔄 [Universal] Смена тикера с MSFT на META - очистка позиций   ← React видит смену
📡 [Universal] Опционы обновлены от расширения: {fromExtension:1, manual:3, total:4}  ← но мержит 3 "manual"
```

**Причина:** `useExtensionData.js` при синхронизации от расширения сохраняет "manual" позиции (добавленные вручную или из предыдущих сессий), не очищая их при смене тикера.

**Файл:** `UniversalOptionsCalculator.jsx:1596`, `useExtensionData.js`

**Решение:** При смене `selectedTicker` сбрасывать manual-позиции если их тикер не совпадает с новым.

**Статус:** Открыт. Требует фикса на фронтенде калькулятора.

# SDD Workflow — Автоматический пайплайн разработки

## Философия

Разработчик не должен помнить процесс. Процесс сам себя ведёт.
Каждый пайплайн — это цепочка фаз с чекпоинтами. Переход к следующей фазе — только после валидации предыдущей.

**Принцип:** логика пайплайнов — глобальная (одинаковая везде). Конфигурация — локальная (разная в каждом проекте).

## Конфигурация проекта

При запуске `/init` агент спрашивает и сохраняет в `CLAUDE.md` проекта.

Путь к документации **НЕ фиксированный** — он разный для каждого модуля/задачи. Поэтому:

```
┌──────────────────────────────────────────────────────────────┐
│                  КОНФИГУРАЦИЯ (в CLAUDE.md проекта)           │
│                                                               │
│  ## SDD Config                                               │
│  deploy_cmd: ./deployment/deploy.sh   ← как деплоим         │
│  test_cmd: pytest backend/tests/      ← как тестируем        │
│                                                               │
│  Путь к документации НЕ хранится глобально.                  │
│  docs_path определяется для каждой задачи отдельно:          │
│  - /develop — всегда спрашивает                              │
│  - /fix, /refactor — автопоиск → предложение → подтверждение │
│  - /hotfix — автопоиск ПОСЛЕ деплоя                          │
│  - /amend, /resume — читает из README.md задачи              │
│                                                               │
│  Агент сохраняет путь в README.md задачи (поле: docs_path). │
└──────────────────────────────────────────────────────────────┘
```

**Правило получения docs_path:**

| Команда | Как получает docs_path |
|---------|----------------------|
| `/develop` | Всегда спрашивает (новая фича может быть в новой папке) |
| `/fix` | Автопоиск: ищет ближайшие spec.md/README.md рядом с затронутым кодом → предлагает пользователю → подтверждение |
| `/refactor` | Автопоиск: аналогично /fix — предлагает, пользователь подтверждает |
| `/hotfix` | Автопоиск ПОСЛЕ деплоя: по изменённым файлам ищет ближайшую папку документации → предлагает |
| `/amend` | Читает из README.md задачи (уже сохранён) |
| `/resume` | Читает из README.md задачи (уже сохранён) |

**Принцип:** агент **предлагает**, пользователь **подтверждает или корректирует**. Агент никогда не решает молча.

## GATE — механизм контроля переходов

Ключевой механизм, который гарантирует последовательность фаз. GATE — это проверка, встроенная в начало каждой фазы пайплайна.

```
┌─────────────────────────────────────────────────────────┐
│                    GATE (шлюз)                            │
│                                                          │
│  Перед началом фазы N агент ОБЯЗАН:                     │
│                                                          │
│  1. Найти артефакт фазы N-1                             │
│     ├── Файл существует? ─── НЕТ → СТОП, вернуться     │
│     └── ДА ↓                                            │
│                                                          │
│  2. Валидировать содержимое                              │
│     ├── Обязательные секции есть? ─── НЕТ → дополнить   │
│     └── ДА ↓                                            │
│                                                          │
│  3. Записать в README.md задачи:                        │
│     "GATE N пройден: [дата], артефакт: [файл]"         │
│                                                          │
│  4. Начать фазу N                                       │
└─────────────────────────────────────────────────────────┘
```

**Реализация GATE:**

GATE прописан в тексте каждой slash-команды как явная инструкция. Это часть промпта — агент физически не может пропустить, потому что это его задание. Не хук, не договорённость — инструкция в промпте.

**В CLAUDE.md проекта (constitution):**

«Перед началом любой фазы — проверь GATE. Если GATE не пройден — не продолжай. Это блокирующее требование.»

## Git-фиксация в пайплайнах

```
┌──────────────────────────────────────────────────────────┐
│                GIT В ПАЙПЛАЙНЕ                            │
│                                                           │
│  ВХОД                          ВЫХОД                     │
│  ┌──────────┐                  ┌───────────────────┐     │
│  │checkpoint│                  │    commit          │     │
│  │ (auto)   │   ...работа...   │ type(scope): msg  │     │
│  └──────────┘                  │ Task: task-name    │     │
│                                │ Phase: DONE        │     │
│  Claude Code                   │ Artifacts: spec,   │     │
│  автоматически                 │   plan, verify     │     │
│  создаёт точку                 └───────────────────┘     │
│  отката                                                   │
│                                                           │
│  В README.md задачи фиксируется:                        │
│  - commit_start: abc1234 (автоматический checkpoint)     │
│  - commit_done: def5678 (финальный коммит)               │
│  - changed_files: [список]                               │
└──────────────────────────────────────────────────────────┘
```

**Формат коммита:**
```
type(scope): краткое описание

Task: {task-name}
Phase: {фаза}
Artifacts: {список артефактов}
```

**Что в CLAUDE.md проекта:** правило формата коммитов и обязательные поля Task/Phase.
**Что в slash-командах:** инструкция записать хеши коммитов в README.md задачи.

## Модельная стратегия (Opus / Sonnet)

Фазы пайплайнов распределены между моделями по принципу: **Opus проектирует и проверяет, Sonnet реализует.**

```
┌──────────────────────────────────────────────────────────────┐
│              РАСПРЕДЕЛЕНИЕ МОДЕЛЕЙ ПО ФАЗАМ                    │
│                                                               │
│  OPUS (основной поток)          SONNET (субагенты)           │
│  ─────────────────────          ──────────────────            │
│  ✓ SPEC — проектирование       ✓ BUILD — реализация          │
│  ✓ PLAN — планирование         ✓ FIX — патчинг кода          │
│  ✓ DIAGNOSE — анализ           ✓ REFACTOR — структурные      │
│  ✓ VERIFY — проверка             изменения кода               │
│  ✓ SPEC-SYNC — синхронизация                                  │
│  ✓ DOC — документация                                        │
│                                                               │
│  Глубина анализа важна          Объём кода важен              │
│  → нужна мощная модель          → нужна быстрая модель        │
└──────────────────────────────────────────────────────────────┘
```

**Как это работает:** в фазах реализации Opus запускает субагентов через Agent tool с параметром `model: "sonnet"`. Каждый субагент получает конкретное задание из плана, список файлов и правила кода. Параллельные агенты используются когда задачи независимы.

**Как пользователь видит переключение:** перед запуском Sonnet-фазы агент выводит маркер: `⚙️ BUILD: запуск Sonnet-агентов для реализации` (или аналогичный для FIX/REFACTOR).

| Команда | Фазы на Opus | Фазы на Sonnet |
|---------|-------------|----------------|
| `/develop` | SPEC, PLAN, VERIFY, DOC | BUILD |
| `/fix` | DIAGNOSE, VERIFY, SPEC-SYNC | FIX |
| `/refactor` | SNAPSHOT, VERIFY, SPEC-SYNC | REFACTOR |
| `/hotfix` | VERIFY, DEPLOY, SPEC-SYNC | FIX |
| `/amend` | REOPEN, VERIFY, SPEC-SYNC | FIX |
| `/audit` | Все фазы на Opus | — (диагностический, не меняет код) |

**Способ использования не влияет** — модельная стратегия одинаково работает в CLI, IDE (VS Code) и Web.

### 1. DEVELOP — новая фича / модуль

Полный цикл от идеи до коммита. Review и security check встроены в фазу VERIFY.

```
┌──────────────────────────────────────────────────────────────┐
│  /develop                                                     │
│                                                               │
│  СТАРТ: спросить docs_path для этой задачи                   │
│         ↓                                                     │
│  ┌──────┐ GATE ┌──────┐ GATE ┌──────┐ GATE ┌──────┐  ┌───┐ │
│  │ SPEC │─────▶│ PLAN │─────▶│BUILD │─────▶│VERIFY│─▶│DOC│ │
│  └──┬───┘      └──┬───┘      └──┬───┘      └──┬───┘  └─┬─┘ │
│     │             │             │              │        │    │
│     ▼             ▼             ▼              ▼        ▼    │
│  spec.md      plan.md       код готов    ┌─────────┐ README  │
│  ✓ цель       ✓ покрытие   ✓ линтер    │ review  │ ✓ чек   │
│  ✓ риски      ✓ порядок    ✓ 300 строк  │ + secur.│ ✓ git   │
│  ✓ приёмка    ✓ нет конфл. ✓ паттерны   │ + тесты │ ✓ done  │
│                                          └─────────┘         │
└──────────────────────────────────────────────────────────────┘
```

**Фазы:**

| # | Фаза | Вход | Выход (артефакт) | GATE перед входом |
|---|------|------|------------------|-------------------|
| 1 | SPEC | Описание от пользователя | `spec.md` | — (первая фаза, но docs_path уже спрошен) |
| 2 | PLAN | spec.md | `plan.md` | spec.md существует и валиден |
| 3 | BUILD | plan.md | Изменённые файлы | plan.md существует и валиден |
| 4 | VERIFY | Код | `verify.md` | Код изменён, BUILD завершён |
| 5 | DOC | Всё выше | README.md обновлён | verify.md существует, все проверки ✅ |

**VERIFY включает:**
- Тесты проходят
- Критерии приёмки из spec.md закрыты
- Code review (качество, паттерны, правила)
- Security check (инъекции, XSS, утечки ключей, OWASP top 10)

**При провале VERIFY:**
- VERIFY формирует отчёт с конкретными проблемами и предлагает варианты решения
- Пользователь решает: чиним и идём дальше, или (в редком случае) откатываемся вручную
- Отдельной команды /rollback нет — откат при необходимости делается простыми инструкциями

### 6. AUDIT — документирование реального состояния модуля

Для модулей/задач с отсутствующей, неполной или устаревшей документацией. Результат аудита — **рабочий документ с актуальной документацией**, а не просто список проблем.

```
┌──────────────────────────────────────────────────────────────┐
│  /audit {путь к модулю или задаче}                            │
│                                                               │
│  ┌───────┐    ┌────────┐    ┌────────┐    ┌───────────────┐ │
│  │ SCAN  │───▶│DOCUMENT│───▶│ ASSESS │───▶│   OUTPUT      │ │
│  └──┬────┘    └──┬─────┘    └──┬─────┘    └──┬────────────┘ │
│     │            │             │              │              │
│     ▼            ▼             ▼              ▼              │
│  собрать      описать       оценить      README-audit.md   │
│  всё что      как модуль    расхождения  = актуальная      │
│  есть         работает      между доками документация      │
│  ✓ код        СЕЙЧАС        и реальностью + оценка         │
│  ✓ доки       (из кода,     ✓ что врёт    + рекомендации   │
│  ✓ тесты      рекурсивно)   ✓ что неполно                  │
│  ✓ конфиги                  ✓ что ОК                        │
└──────────────────────────────────────────────────────────────┘
```

**Фазы:**

| # | Фаза | Что делает |
|---|------|-----------|
| 1 | SCAN | Рекурсивно сканирует: код, существующие доки, тесты, конфиги |
| 2 | DOCUMENT | Описывает как модуль реально работает сейчас — из кода, не из старых доков |
| 3 | ASSESS | Сопоставляет с существующей документацией: что соответствует, что врёт, что отсутствует |
| 4 | OUTPUT | Создаёт `README-audit.md` — единый документ |
| 5 | MERGE-PLAN | Предлагает конкретный план слияния: что заменить, что мержить, что оставить как есть |

**Почему README-audit.md, а не перезапись README.md:**

Старые доки могут содержать контекст решений, который из кода не восстановить. Audit создаёт параллельный документ и предлагает план слияния. Пользователь утверждает или корректирует план.

**Структура README-audit.md:**
```markdown
# Audit: {модуль/задача}
Date: {дата}
Path: {путь к модулю}

## Что это и зачем
(описание модуля из кода — что он реально делает)

## Как работает
(архитектура, потоки данных, ключевые механизмы)

## Структура файлов
(дерево с описанием ответственности каждого файла)

## Зависимости
(от чего зависит, что зависит от него)

## Расхождения с документацией
| Документ | Проблема | Критичность |
|----------|----------|-------------|
| spec.md  | Описывает 3 режима, в коде их 5 | 🔴 высокая |
| plan.md  | Ссылается на удалённый файл | 🟡 средняя |
| README.md | Не упоминает новый кэш | 🟡 средняя |

## Рекомендации
(что стоит обновить в первую очередь, приоритизированный список)

## План слияния
| Документ | Действие | Что именно |
|----------|----------|-----------|
| spec.md  | Заменить секцию X | Актуальное описание из аудита |
| plan.md  | Удалить | Ссылается на несуществующий код |
| README.md | Дополнить | Добавить описание кэша |
```

**Два режима:**

| Ситуация | Что создаёт |
|----------|-------------|
| Документации нет совсем | `README-audit.md` = полная документация модуля, сгенерированная из кода |
| Документация есть, но устарела | `README-audit.md` = актуальная документация + секция расхождений |

**После аудита:** каждый пункт из «Рекомендаций» выполняется через `/fix` (обновление спеки) или `/develop` (если нужна новая функциональность).

## Синхронизация документации модуля (MODULE-SYNC)

Двухуровневая структура: **модуль** (spec.md, plan.md модуля) → **задачи** (spec.md, plan.md задач внутри модуля).

Документация задачи — исторический снимок: что было сделано и почему на тот момент. Не обновляется задним числом.
Документация модуля — живой контракт: как модуль работает сейчас. Держится актуальной.

```
┌──────────────────────────────────────────────────────────────┐
│                    MODULE-SYNC                                │
│                                                               │
│  MODULE-SYNC — часть фазы SPEC-SYNC.                         │
│  Любой пайплайн с фазой SPEC-SYNC:                          │
│                                                               │
│  1. Определить затронутые файлы                              │
│     ↓                                                         │
│  2. Найти spec.md и plan.md МОДУЛЯ                           │
│     (родительская директория docs_path задачи,               │
│     ровно 1 уровень вверх)                                   │
│     ↓                                                         │
│  3. Затрагивает ли изменение описанное поведение модуля?     │
│     ├── ДА → обновить spec.md и/или plan.md модуля           │
│     │        записать в README модуля:                        │
│     │        "[дата] spec.md обновлена в ходе {pipeline}"    │
│     └── НЕТ → пропустить                                     │
│                                                               │
│  Документацию ДРУГИХ ЗАДАЧ — НЕ трогать.                     │
│  Задачи = исторические снимки, не обновляются задним числом. │
│                                                               │
│  Пример:                                                     │
│  /fix в задаче tools/module_v2/tasks/fix-timeout/            │
│     │                                                         │
│     ├── tools/module_v2/spec.md  ← обновить если затронуто   │
│     ├── tools/module_v2/plan.md  ← обновить если затронуто   │
│     └── tools/module_v2/tasks/other-task/spec.md ← НЕ трогать│
└──────────────────────────────────────────────────────────────┘
```

**Какие команды запускают MODULE-SYNC:**

| Команда | MODULE-SYNC | Почему |
|---------|------------|--------|
| `/fix` | Да | Фикс может изменить поведение, описанное в спеке модуля |
| `/refactor` | Да | Рефакторинг меняет структуру модуля |
| `/hotfix` | Да (постфактум) | Срочный фикс мог изменить поведение модуля |
| `/amend` | Да | Коррекция может изменить поведение модуля |
| `/develop` | Нет | Создаёт новую задачу, не меняет существующее поведение |
| `/audit` | Нет | Только документирует, не меняет код |

## Артефакты — файлы-чекпоинты

Путь к артефактам = `docs_path`, который определяется при старте каждого пайплайна и сохраняется в README.md задачи.

### Конвенция именования файлов

| Тип | Формат имени | Пример |
|-----|-------------|--------|
| Постоянные артефакты | `{индекс}_{имя}.md` | `1_spec.md`, `2_plan.md` |
| Хронологические артефакты | `{YYYY-MM-DD}_{тип}.md` | `2026-04-01_verify.md` |
| Файлы-следы | `{YYYY-MM-DD}_{тип}-{краткое-имя}.md` | `2026-04-01_fix-timeout.md` |
| Маркер завершения | `_DONE` | `_DONE` |
| Навигация/статус | `README.md` | `README.md` |

Индексы обеспечивают правильную сортировку в дереве. Даты — хронологический порядок.

### Привязка к задаче

Каждый пайплайн ОБЯЗАН работать в папке задачи. Если `/fix` или `/hotfix` запускается без связанной задачи — агент создаёт мини-задачу:

```
task-hotfix-2026-04-20-crash/     ← мини-задача (без spec/plan)
├── README.md                     ← Pipeline: /hotfix, Status: ✅ DONE
├── 2026-04-20_hotfix-crash.md    ← след
└── _DONE
```

**Правило:** «бездомных» фиксов не бывает. Любой пайплайн оставляет след в папке задачи. Нет задачи — создаётся мини-задача.

### Структура полной задачи

```
task-websocket-reconnect/                         ← /develop, завершена
├── _DONE                                         ← маркер завершения
├── README.md                                     ← статус, GATE Log, git-хеши
├── 1_spec.md                                     ← контракт (для человека)
├── 2_plan.md                                     ← техзадание (для ИИ)
├── 2026-03-30_verify.md                          ← протокол проверки
├── 2026-04-01_fix-timeout.md                     ← след /fix
├── 2026-04-10_fix-ssl-error.md                   ← след /fix
└── 2026-04-15_refactor.md                        ← след /refactor
```

### spec.md — контракт с продактом (для человека)

Пишется на языке продукта, без кода, без методов, без технических деталей.

| Секция | Обязательная | Что содержит |
|--------|-------------|-------------|
| Цель | Да | Зачем это делаем, какую проблему решаем |
| Поведение | Да | Сценарии на языке пользователя: «при X происходит Y» |
| Ограничения | Да | Что НЕ делаем, границы задачи |
| Риски | По ситуации | Что может пойти не так |
| Критерии приёмки | Да | Как проверить что готово — без кода, на уровне поведения |

**Что НИКОГДА не попадает в spec.md:** имена файлов, функций, методов, примеры кода, технические чек-листы.

### plan.md — техзадание для агента (для ИИ)

Содержит всё, что нужно ИИ для реализации. Состав секций **адаптивный** — агент включает только релевантные для конкретной задачи.

| Секция | Когда включать |
|--------|---------------|
| Порядок действий | Всегда |
| Затрагиваемые файлы | Всегда |
| API-контракты / интерфейсы | Если есть взаимодействие между модулями |
| Примеры кода / паттерны | Если паттерн неочевидный или нестандартный |
| Миграции данных | Если меняется структура БД |
| Задание на автотесты | Если есть что тестировать автоматически |
| Обратная совместимость | Если есть публичные API или зависимые модули |
| Конфигурация / env | Если нужны новые переменные окружения |
| Критерии приёмки (технич.) | Всегда — техническая версия критериев из spec.md |

**Принцип:** plan.md разный для разных задач. Простой баг-фикс → 3 секции. Новый модуль с API → 8 секций. Агент сам определяет нужный набор.

### verify.md — результат проверки (для ИИ и человека)

Фиксирует что именно проверялось и с каким результатом. Создаётся автоматически в фазе VERIFY.

| Секция | Что содержит |
|--------|-------------|
| Тесты | Какие запущены, результат (pass/fail), покрытие |
| Критерии приёмки | Список из spec.md с отметками ✅/❌ |
| Code review | Соответствие паттернам, правилу 300 строк, стилю проекта |
| Security | Проверка OWASP top 10: инъекции, XSS, утечки ключей, и т.д. |
| Итог | ✅ Все проверки пройдены / ❌ Блокеры: {список} |

### README.md — два контекста использования

`README.md` используется в двух разных ролях:

| Где | Роль | Содержимое |
|-----|------|-----------|
| В обычных папках проекта | **Навигация для ИИ** | Назначение папки, список подпапок/файлов с кратким описанием |
| В `docs_path` задачи | **Статус задачи** | Pipeline, Status, docs_path, Git-хеши, GATE Log, Change Log, Amendments |

`README.md` в корне каждой папки — **служебный навигационный файл**. Его цель — дать ИИ-агенту быстрое понимание: что здесь лежит, какова структура подпапок, где что искать.

- Не для человека, а для контекста агента
- Содержит: назначение папки, список подпапок/файлов с кратким описанием
- В `docs_path` задачи README.md дополнительно содержит: статус, GATE Log, git-хеши, docs_path

**README.md задачи содержит:**

### Описание команд

| Команда | Когда | Что делает |
|---------|-------|-----------|
| `/init` | Новый проект | Создаёт/проверяет CLAUDE.md проекта (constitution, конфиг). Спрашивает deploy_cmd, test_cmd |
| `/audit` | Старый проект с документацией | Сканирует модуль, создаёт `README-audit.md` — актуальная документация + оценка расхождений |
| `/develop` | Новая фича/модуль | Спрашивает docs_path → SPEC→PLAN→BUILD→VERIFY(+review+security)→DOC |
| `/fix` | Баг (не срочный) | Автопоиск docs_path → DIAGNOSE→FIX→VERIFY→SPEC-SYNC |
| `/refactor` | Улучшение структуры | Автопоиск docs_path → SNAPSHOT→REFACTOR→VERIFY→SPEC-SYNC |
| `/hotfix` | Баг в проде | FIX→VERIFY→DEPLOY→SPEC-SYNC (автопоиск docs_path после деплоя) |
| `/amend` | Коррекция закрытой задачи | Читает docs_path из README → REOPEN→FIX→VERIFY→SPEC-SYNC |
| `/status` | Где мы сейчас? | Ищет все README.md с GATE Log в проекте, показывает статус |
| `/resume` | Продолжить после перерыва | Читает README.md задачи, определяет фазу по артефактам, продолжает |
| `/deploy` | Деплой | Только если задача завершена, запускает deploy_cmd |

## Принципы (constitution)

Эти правила действуют во ВСЕХ пайплайнах и прописываются в CLAUDE.md каждого проекта:

1. **Спека — источник правды.** Код реализует спеку, не наоборот
2. **GATE обязателен.** Перед каждой фазой — проверка артефакта предыдущей. Блокирующее требование
3. **Минимальные изменения.** Не трогай то, что не относится к задаче
4. **Спека всегда актуальна.** Любое изменение поведения → обновление spec.md
5. **Всё в репозитории.** Спеки, планы, результаты проверки — рядом с кодом
6. **Путь всегда подтверждается.** Агент может предложить docs_path (автопоиск), но пользователь всегда подтверждает. `/develop` — всегда спрашивает. `/resume`, `/amend` — читает из README задачи
7. **Git-фиксация.** Каждый пайплайн: входной checkpoint → работа → выходной коммит с тегом задачи
8. **Security в каждом VERIFY.** Проверка безопасности — часть верификации, не отдельный шаг
9. **Агент не спрашивает то, что может решить сам.** Вопросы — только для продуктовых решений
10. **Каждый пайплайн привязан к задаче.** «Бездомных» фиксов не бывает. Если задачи нет — создаётся мини-задача. Любой след остаётся в папке задачи
11. **Audit-check при входе в папку.** Перед началом работы в любой папке — проверь наличие `README-audit.md`. Если он есть — документация может быть неактуальна. Предупреди пользователя и предложи сначала разрешить расхождения. `README-audit.md` — временный артефакт: после разрешения расхождений он удаляется или архивируется

## Что идёт куда

| Что | Где | Почему |
|-----|-----|--------|
| Логика пайплайнов | `~/.claude/commands/*.md` | Глобальная, одинаковая во всех проектах |
| Constitution (принципы) | `CLAUDE.md` проекта | Может отличаться между проектами |
| deploy_cmd, test_cmd | `CLAUDE.md` проекта | Специфично для проекта |
| Правила кода | `~/.claude/CLAUDE.md` | Глобальные, личные предпочтения |
| docs_path задачи | `README.md` задачи | Специфичен для каждой задачи |
| GATE Log | `README.md` задачи | История прохождения фаз |
| Артефакты | `{docs_path}/` задачи | Рядом с документацией модуля |
| README.md (навигация) | Корень каждой папки | Служебный файл для ИИ: что здесь лежит |

## Сводный чек-лист реализации

Все файлы, которые нужно создать для запуска SDD Workflow:

```
~/.claude/commands/           ← 10 файлов
├── init.md                   ~80-100 строк
├── develop.md                ~150-200 строк
├── fix.md                    ~120-150 строк
├── refactor.md               ~120-150 строк
├── hotfix.md                 ~120-150 строк
├── amend.md                  ~100-120 строк
├── audit.md                  ~100-120 строк
├── status.md                 ~40-60 строк
├── resume.md                 ~40-60 строк
└── deploy.md                 ~30-40 строк
                              ────────────────
                              Итого: ~900-1100 строк
```

**Порядок создания:**
1. `init.md` — первым, потому что он настраивает CLAUDE.md проекта
2. `develop.md` — основной пайплайн, самый полный
3. `fix.md`, `refactor.md`, `hotfix.md`, `amend.md` — по аналогии с develop
4. `audit.md` — отдельная логика, без GATE
5. `status.md`, `resume.md`, `deploy.md` — утилиты

**Процесс создания каждой команды (обязательный):**
1. Черновик на русском — полная версия со всеми фазами, GATE-блоками, шаблонами
2. Ревью пользователем — утверждение логики, фаз, артефактов
3. Минимизация — после утверждения:
   - Перевод на английский (~40-50% экономии токенов)
   - Убрать диаграммы, пояснения «почему», многословные описания
   - GATE-блоки сжать до однострочников: `GATE: verify {file} exists in {docs_path}, has sections: {list}. Log to README.`
   - Общие механизмы (MODULE-SYNC, формат коммита) НЕ дублировать — ссылка на constitution: `Follow MODULE-SYNC from constitution`
   - Целевой объём: ~60-70% от черновика

**Оптимизация constitution (в CLAUDE.md проекта):**
- Constitution на английском, каждый принцип — 1-2 строки максимум
- Содержит общие механизмы (MODULE-SYNC, Git Convention), чтобы промпты команд на них ссылались, а не дублировали

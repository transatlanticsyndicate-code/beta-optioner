# Handoff в новый проект калькулятора

**Источник:** beta.optioner.online (старый калькулятор, CalculatorV2)
**Назначение:** calc.optioner.online (переписка с нуля)
**Актуально на:** 2026-05-05, версия v42 на проде

---

## Что это за папка

Эта папка — спецификации поведения и решений старого калькулятора, которые **обязательно** должны быть учтены при разработке нового. Каждый документ описывает одну сфокусированную тему: контекст, корень проблемы, выбранное решение, формулы, сценарии тестирования и чек-лист переноса.

Документы написаны для разработчика нового проекта, который старый код не видел и видеть не должен — все решения и формулы изложены текстом и псевдокодом.

## Рекомендуемый порядок чтения для разработчика нового проекта

1. **`signed-amounts-base-asset-block.md`** — базовый контракт блока «Базовый актив», задаёт фундамент для остального.
2. **`leverage-base-asset.md`** — расширяет первый плечом.
3. **`fact-pl-anchor-quantity-scaling.md`** — отдельная фича таблицы опционов (можно читать независимо, но раньше чем pl-total).
4. **`pl-total-single-source-of-truth.md`** — архитектурное правило, объединяющее всё. Читать последним.

Все документы построены по одной структуре: «Зачем → Корень → Решение → Формулы → Параметры → Сценарии тестирования → Чек-лист переноса → Открытые вопросы → История». Структура повторяется намеренно, чтобы можно было быстро найти нужную секцию в любом из документов.

## Что НЕ покрыто handoff'ами (но было сделано в старом проекте)

Эти темы реализованы, задеплоены, но отдельной спецификации для нового проекта не имеют:

| Тема | Где описано в старом проекте | Стоит ли переносить |
|---|---|---|
| Система статусов сохранённых позиций (`pending` / `standard`, кнопка «🔒 Зафиксировать», health-check расширения TradingView) | `tasks/feature-position-statuses/2026-05-05_develop-position-statuses.md` | Если в новом проекте есть БД сохранённых позиций — да, как референс реализации. Если нет — пропустить. |
| Расширение Chrome `OptionsCPbuttons` для парсинга TradingView | `EXTENTIONS/OptionsCPbuttons/` (отдельный проект) | Расширение единое для обоих калькуляторов. Если новый калькулятор тоже принимает данные от расширения — нужно описать API сообщений отдельно. |
| Расширение `IBKR_Bridge` для отправки ордеров в TWS | `EXTENTIONS/IBKR_Bridge/` (отдельный проект) | Аналогично — отдельный проект. Атрибуты `data-bid`/`data-ask` в DOM таблицы — это контракт между калькулятором и расширением, его описать в момент готовности. |

Если новый калькулятор должен интегрироваться с расширениями TradingView или IBKR Bridge — стоит сделать отдельный handoff про **протокол сообщений между расширением и калькулятором**, потому что в старом проекте этот контракт неявный (разбросан по коду).

## Как поддерживать актуальность

Когда в старом проекте делается фикс или фича, затрагивающая поведение, описанное в каком-либо handoff:

1. **Обновить соответствующий документ в той же сессии** — не «потом, как-нибудь».
2. **Поднять секцию «История» в конце документа** — добавить строку с датой, коммитом и кратким описанием.
3. Если фикс отменяет ранее задокументированное решение — не удалять старую секцию, а перенести её в «Историю» с пометкой «отвергнуто, причина:» и описать новый подход в основной части.

Если документ описывает решение, которое в коде уже не применяется (как было с `pl-total-single-source-of-truth.md` после переписывания на финальный подход) — это критическая ошибка для нового проекта. Перед каждой передачей handoff'ов — обязательная сверка с актуальным состоянием кода.

## 1. Якорь Fact P&L не применяется на дату экспирации

### 1.1. Зачем

В старом калькуляторе у каждой строки опционов есть ячейка «Fact P&L». Пользователь вводит в неё реальный P&L своей открытой позиции (по отчёту брокера) и калькулятор использует это значение как якорь: при движении симулируемой цены или дней до экспирации калькулятор показывает не чисто-теоретический P&L (Black-Scholes / Black-76), а скорректированное значение, отталкиваясь от введённого якоря. Формула:

```
displayed_PL = actualPL × (currentQty / anchorQty) + (theoretical_PL_now − theoretical_PL_at_anchor)
```

Это компенсирует неточности теоретики — спред, корректировки, рыночные эффекты, которые модель не учитывает.

**Проблема:** на дату экспирации (`daysToExp = 0`) теоретическая модель сама уходит в чистый intrinsic value (без временной стоимости) — и это математически точное значение. Применять якорь, созданный для компенсации ошибок теоретики *до* экспирации, на самой экспирации — значит искажать точное число разностью `(pl − plAtAnchor)` ради нулевой пользы. Без защиты пользователь, скользя слайдером DTE до 0, получал P&L, зависящий от введённого Fact P&L и зафиксированной якорной цены — это математически неверно.

### 1.2. Корень

Якорь применялся одинаково и до экспирации, и на ней. Условие входа в якорный блок проверяло только наличие `actualPL` и факт, что текущий день симуляции ≥ дня ввода якоря — но не учитывало, истёк ли опцион в текущей точке симуляции.

### 1.3. Решение

Добавлена проверка `daysToExp > 0` перед применением якоря — во всех местах, где якорь используется. Если опцион в текущей точке симуляции на экспирации или после неё, якорный блок целиком пропускается, остаётся чистая формула:

```
P&L_на_экспирации = (intrinsic(S_target) − entry_price) × qty × multiplier   // Buy
P&L_на_экспирации = (entry_price − intrinsic(S_target)) × qty × multiplier   // Sell

intrinsic_call(S, K) = max(0, S − K)
intrinsic_put (S, K) = max(0, K − S)
```

**Граница:** строго `daysToExp > 0` (не `>= 0`). Функция получения остатка дней на дату экспирации возвращает ровно `0`, и при этом значении якорь не запускается.

**Где применить защиту:** во всех точках использования якоря — это единое правило, не должно быть исключений. В старом проекте таких точек оказалось четыре:

| # | Что | Где в коде |
|---|---|---|
| 1 | P&L строки в таблице опционов | `OptionsTableV3.jsx` ≈ строка 1219 |
| 2 | Обратный расчёт цены закрытия (Close Price) | `OptionsTableV3.jsx` ≈ строка 1395 |
| 3 | Сценарий выхода по цене (S2) в ExitCalculator | `usePositionExitCalculator.js` ≈ строка 470 |
| 4 | Сценарий выхода по времени (S3) в ExitCalculator | `usePositionExitCalculator.js` ≈ строка 666 |

### 1.4. Сценарии тестирования

| # | Сценарий | Ожидание |
|---|---|---|
| A1 | Опцион с Fact P&L = 100, слайдер DTE до 0 | P&L = `(intrinsic − entry) × qty × multiplier`, не зависит от Fact P&L |
| A2 | Тот же опцион, слайдер DTE = 5 (до экспирации) | P&L применяет якорную формулу, как обычно |
| A3 | Колонка Close на DTE=0 | Цена закрытия = intrinsic value (без коррекций) |
| A4 | Сценарии S2/S3 в ExitCalculator на дате экспирации | P&L каждого сценария не зависит от Fact P&L |

### 1.5. Чек-лист переноса

- [ ] Якорь применяется только когда опцион в текущей точке симуляции **ещё активен** (`daysToExp > 0`).
- [ ] Граница строго `> 0`, не `>= 0`.
- [ ] Защита нужна **во всех местах** применения якоря, без исключений (не «защитить только основную колонку»).
- [ ] Юнит-тест: для опциона с введённым Fact P&L на DTE=0 значение P&L равно intrinsic-формуле и не зависит от `actualPL` / `actualPLPrice`.

## 2. MAX убыток поддерживает положительный флор

### 2.1. Зачем

Метрика «MAX убыток» описывает **худший P&L стратегии на дату экспирации** — `min(P&L)` по диапазону цен. У большинства стратегий это число отрицательное (реальный убыток), но у части — например, у коллара (long stock + buy put + sell call) или у дебетного спреда с подходящим net premium — `min(P&L)` на экспирации **положителен**: даже в худшем сценарии стратегия гарантированно не уходит в минус. В этой точке `min(P&L) ≥ 0` — это «гарантированный минимальный профит».

**Проблема:** старый калькулятор такой случай не показывал.

- В шапке метрик: при `maxLoss ≥ 0` рисовался прочерк («—») вместо числа.
- В блоке «Базовый актив»: значение бралось через `Math.abs(...)` и в JSX печаталось как `'−$ ' + value` — знак терялся, литеральный минус становился частью UI. Пользователь видел «−$96» красным вместо реального «+$96».

Пользователь не понимал, что построил стратегию с гарантированным мин-профитом.

### 2.2. Корень

Двойственная природа метрики:

- Семантически это «худший P&L», и его значение — просто `min(P&L)`.
- Визуально проектировалось как «всегда красное число с минусом».

В шапке метрик условие фильтровало неотрицательные значения (`maxLoss < 0 ? show : '—'`). В блоке «Базовый актив» использовался `Math.abs` и захардкоженный минус в JSX.

Дополнительная техническая ловушка: при пустом массиве P&L `Math.min(...[]) = +Infinity`, `Math.max(...[]) = -Infinity` — эти значения утекали в UI без отдельной защиты.

### 2.3. Решение

#### 2.3.1. Селектор метрики

`min(P&L)` и `max(P&L)` возвращаются **со знаком**, как есть. Никаких `Math.abs` в селекторе. Защита от пустых массивов:

```
sourceArr = expirationPLArray.length > 0 ? expirationPLArray : totalPLArray
maxProfit = sourceArr.length > 0 ? Math.max(...sourceArr) : 0
maxLoss   = sourceArr.length > 0 ? Math.min(...sourceArr) : 0
```

#### 2.3.2. Шапка метрик и блок «Базовый актив»

Метрика всегда показывает значение со знаком, цвет — динамический по знаку:

| `maxLoss` | Цвет | Знак | Семантика |
|---|---|---|---|
| `< 0` | красный | `−$N` | реальный максимальный убыток |
| `> 0` | зелёный | `+$N` | гарантированный минимальный профит на экспирации |
| `= 0` | серый | `$0` | break-even (ровно ноль в худшей точке) |

Тултип: «Худший P&L стратегии НА ДАТУ ЭКСПИРАЦИИ. Отрицательное — максимальный убыток. Положительное — гарантированный мин-профит (стратегия не может уйти в минус)».

#### 2.3.3. Логика лимита убытков

В блоке «Базовый актив» есть плашка «лимит убытка превышен / в рамках лимита». Лимит — положительное число (% от депозита, делённого на число инструментов). Чтобы корректно сравнивать со значением со знаком, ввести **отдельную переменную «экспозиция к убытку»**:

```
lossExposure = maxLoss < 0 ? Math.abs(maxLoss) : 0
```

Это единственное место, где модуль уместен: лимит «потерь» нарушается только когда есть реальный убыток. Если `maxLoss ≥ 0`, фактической экспозиции к убытку нет и плашка лимита всегда «в рамках».

### 2.4. Сценарии тестирования

| # | Стратегия | Ожидание |
|---|---|---|
| B1 | Голый Buy Call | MAX убыток < 0, красный, со знаком «−». Risk/Reward — реальное число. |
| B2 | Коллар (long 200 BLDR + Buy PUT 95×2 + Sell CALL 110×2) с net-кредитом, гарантирующим положительный флор | MAX убыток > 0, зелёный, со знаком «+». Risk/Reward = ∞. В блоке «Базовый актив» — то же значение зелёным. Плашка лимита всегда «в рамках». |
| B3 | Дебетный спред в точке зеро-ноль | MAX убыток = $0, серый. |
| B4 | Стратегия без полных опционов | MAX убыток показывает «—», цвет нейтральный. |

### 2.5. Чек-лист переноса

- [ ] Селектор `min/max` возвращает значения **со знаком**, без `Math.abs`.
- [ ] Защита от пустых массивов: `sourceArr.length > 0 ? Math.min(...sourceArr) : 0`. Аналогично для `Math.max`. Никакого `±Infinity` в UI.
- [ ] Цвет «MAX убыток» — динамический: `< 0` → красный, `> 0` → зелёный, `= 0` → серый.
- [ ] Знак в строке: для `> 0` показывается явный «+», для `< 0` — «−», для `= 0` — без знака.
- [ ] Захардкоженного литерального минуса в JSX быть не должно.
- [ ] Для логики лимита ввести `lossExposure = max(0, -maxLoss)`. Лимит превышается только когда `lossExposure > limit`.
- [ ] Тултип объясняет случай положительного флора.
- [ ] Не показывать прочерк «—» только потому, что значение неотрицательное — это потеря информации.

### 2.6. Открытые вопросы

1. **Переименование метрики.** «MAX убыток» — устоявшийся термин, но семантически неточный для стратегий с положительным флором. Возможно «MAX P&L на экспирации» или «Худший P&L». Решение продакта.
2. **Range расчёта.** Сейчас `[currentPrice × 0, currentPrice × 2]`. Для голых short это даёт усечённый ответ. Можно отдельно показывать «−∞» по аналогии с «∞» у MAX прибыли.

## 3. Иконка видимости работает в любом режиме (замочек убран)

### 3.1. Зачем

В таблице опционов и в строках базового актива каждая запись имеет иконку слева — глазок (Eye) для видимой записи, зачёркнутый глазок (EyeOff) для временно скрытой. Клик по иконке исключает строку из расчётов калькулятора и метрик, не удаляя её. Это стандартный приём для «что-если»-анализа: пользователь хочет посмотреть, как изменится P&L и риск, если убрать одну ногу стратегии.

**Проблема:** для «зафиксированных» позиций (`isLockedPosition === true` — у позиций, загруженных из сохранения и помеченных как реально открытые) иконка превращалась в красный замочек (Lock) и переставала кликаться. Семантика была «эта позиция реальна, её нельзя скрыть». На практике это блокировало основной аналитический сценарий: пользователь хотел временно посмотреть, что будет без одной ноги, — но не мог из-за замочка.

### 3.2. Решение

Иконка замочка убрана полностью — никогда не показывается, ни в таблице опционов, ни в блоке базового актива. Всегда рендерится пара Eye/EyeOff с работающим обработчиком `toggleVisibility(id)`. Зафиксирована позиция или нет — на иконку видимости это не влияет.

**Семантическое обоснование:** статус «зафиксирована» уже виден в шапке позиции (бейджик «🔒 Зафиксирована»), дублировать его на каждой строке таблицы избыточно. Видимость и зафиксированность — независимые атрибуты, и их наложение через одну иконку путает пользователя больше, чем помогает.

**Что не меняется:** `isLockedPosition` остаётся как флаг для блокировки **редактирования** числовых полей (количество, премия, страйк, дата) — это правильное поведение, не позволяющее случайно поправить параметры реально открытой позиции. Только иконка видимости теперь работает всегда.

### 3.3. Сценарии тестирования

| # | Сценарий | Ожидание |
|---|---|---|
| C1 | Незафиксированный опцион, клик по глазку | Глазок → перечёркнутый глазок. P&L строки серый/блёклый. ИТОГО таблицы пересчитывается без этой строки. |
| C2 | Зафиксированный опцион (загружена как `standard`), клик по глазку | То же самое — глазок → перечёркнутый. Никаких замочков на строке. |
| C3 | Зафиксированный опцион, попытка изменить количество/премию | Поля заблокированы (как и было раньше). Меняется только поведение иконки видимости, не редактирование. |
| C4 | Базовый актив, клик по глазку | Аналогично C1/C2 — работает в любом режиме. |

### 3.4. Чек-лист переноса

- [ ] У каждой строки опциона и базового актива иконка видимости — Eye/EyeOff, **независимо** от `isLockedPosition` или аналогичного флага.
- [ ] Клик по иконке всегда вызывает `toggleVisibility(id)`. Никакой `disabled`-логики на иконке.
- [ ] Замочек на самой иконке видимости не нужен. Статус «зафиксирована» показывается отдельно (бейджик в шапке строки/позиции).
- [ ] `isLockedPosition` (или эквивалент) остаётся как флаг для блокировки редактирования полей, но не для иконки видимости.

## 4. Чекбоксы и пакетное удаление на странице сохранений

### 4.1. Зачем

Страница со списком сохранённых конфигураций показывает таблицу со столбцами «Дата», «Тикер», «Тип», «Статус», «Название», «Автор», «Действия». В колонке «Действия» — кнопки «Редактировать» и «Удалить», работающие построчно. Также есть кнопки «Удалить всё» и «Сбросить фильтры».

**Проблема:** пользователю нужно удалить N конфигураций по выбору — например, 5 мусорных черновиков, оставив остальные. Старый UI требовал нажимать «Удалить» для каждой и подтверждать каждое удаление через `window.confirm`. Для 10 записей — 30 действий.

### 4.2. Решение

В таблицу добавлена первая колонка с чекбоксом. Шапка таблицы — master-чекбокс с тремя состояниями:

| Состояние | Условие |
|---|---|
| `unchecked` | ни одна запись текущей страницы не выделена |
| `checked` | все записи текущей страницы выделены |
| `indeterminate` | выделена часть |

**Клик по master-чекбоксу:** если `checked` или `indeterminate` — снимает выделение со всех записей текущей страницы. Иначе — добавляет все записи текущей страницы в выделение. Записи, скрытые фильтрами или находящиеся на других страницах пагинации, master-чекбоксом не затрагиваются.

**Кнопка «Удалить выбранные (N)»** в шапке страницы рядом с «Удалить всё»:

1. Один общий `confirm` — «Удалить N конфигураций?». Не N подтверждений.
2. Параллельные DELETE-запросы через `Promise.allSettled` — один сбой не блокирует остальные.
3. Сводный отчёт: «Удалено: M. Не удалось удалить: K» (только если K > 0; молчаливый успех если всё удалилось).
4. После завершения — `setSelectedIds(new Set())` и перезагрузка списка.

**Сброс выделения:**

- При смене любого фильтра — выделение сбрасывается (иначе пользователь рискует случайно удалить записи, скрытые текущим фильтром).
- При смене страницы пагинации — выделение **сохраняется** (пользователь может пройти по 5 страницам, выделяя по 2 записи на каждой, и одной кнопкой удалить все 10).

### 4.3. Право на удаление

В старом проекте была политика «удалять можно только свои конфигурации» (проверка `author === currentUserName` во фронте). На текущем этапе это ограничение **снято** — выделять и удалять можно любые записи; авторизация остаётся за backend. Если backend откажет, фронт покажет «Не удалось удалить: K».

**Для нового проекта это решение продакта:** хотите ли вы политику «только свои» во фронте, или полагаетесь только на серверную авторизацию. Технически в коде должен быть один параметр `userId` (или эквивалент), передаваемый в DELETE; backend сам решает, имеет ли пользователь право.

### 4.4. Замечания по реализации

- **Native checkbox vs UI-обёртка.** В старом проекте использован нативный `<input type="checkbox">` с tailwind-классами, а не радиксовая обёртка из `components/ui/checkbox`. Причина — обёртка была написана как `.tsx` с алиасом, который CRA-сборка не разрешала, и build падал. В новом проекте, если есть нормальная UI-библиотека, лучше использовать обёртку — она доступнее (focus ring, ARIA), но математика та же.
- **Indeterminate через ref.** У нативного checkbox нельзя задать `indeterminate` через атрибут — только через `element.indeterminate = true`. В React это делается через `ref={el => { if (el) el.indeterminate = ... }}`.
- **Производительность.** `Set<id>`, иммутабельные обновления (`new Set(prev); next.add(id)`). При 50 записях на странице бесплатно. Если в новом проекте записей много (тысячи), стоит предусмотреть виртуализацию.

### 4.5. Сценарии тестирования

| # | Сценарий | Ожидание |
|---|---|---|
| D1 | Выделить 3 записи на странице, нажать «Удалить выбранные» | Один `confirm`, три параллельных DELETE, выделение сбрасывается, список перезагружается. |
| D2 | Выделить 5 на стр.1, перейти на стр.2, выделить 2, нажать «Удалить выбранные» | Удаляются все 7, кнопка показывает «(7)» до клика. |
| D3 | Выделить 3, поменять фильтр по тикеру | Выделение сброшено. Кнопка «(N)» исчезает. |
| D4 | Master-чекбокс: 0/50 на странице | Клик → 50/50. Повторный клик → 0/50. |
| D5 | Master-чекбокс: 5/50 (indeterminate) | Клик снимает выделение со всех. («Снимать», а не «дополнить» — обычно при частичном выделении пользователь хочет «всё убрать».) |
| D6 | Сервер отверг 1 из 5 (например, истекший токен) | «Удалено: 4. Не удалось удалить: 1». Список перезагружается, оставшаяся 1 видна. |

### 4.6. Чек-лист переноса

- [ ] Колонка с чекбоксом в таблице сохранений — первая.
- [ ] Master-чекбокс в шапке поддерживает три состояния: `checked`, `indeterminate`, `unchecked`. Логика клика — переключает по правилу из §4.2.
- [ ] Master-чекбокс работает только по записям **текущей страницы пагинации**, не по всему отфильтрованному списку и не по всей БД.
- [ ] Состояние выделения хранится как `Set<id>`, иммутабельные обновления.
- [ ] Сброс выделения при смене любого фильтра. Сохранение выделения при смене страницы пагинации.
- [ ] Кнопка «Удалить выбранные (N)» — активна при `selectedIds.size > 0`, рядом с «Удалить всё».
- [ ] Удаление через `Promise.allSettled`, не `Promise.all` — один сбой не блокирует остальные.
- [ ] Один общий `confirm` перед удалением, не N подтверждений.
- [ ] Сводный отчёт об ошибках только когда `failed > 0`. Молчаливый успех если всё удалилось.
- [ ] После удаления — сброс выделения + перезагрузка списка.
- [ ] Решение продакта: возвращать ли политику «только свои» во фронте, или оставить серверную авторизацию.

### 4.7. Открытые вопросы

1. **Master-чекбокс по всему отфильтрованному списку.** Сейчас работает только по странице. Если у пользователя 200 записей и он хочет выделить ВСЕ отфильтрованные — нужен отдельный механизм («выделить все 187» после выделения страницы), как в Gmail. UX-фича уровня middle-priority.
2. **Индикатор прогресса при пакетном удалении.** Сейчас фронт ставит `loading=true`, но не показывает «Удалено M из N». Для большого N стоит добавить.

## 5. Сводный чек-лист переноса

Когда в новом проекте будут реализованы соответствующие фичи, проверить, что учтены все четыре пункта:

- [ ] **Якорь Fact P&L** не применяется на дату экспирации (`daysToExp > 0`) — во всех местах применения.
- [ ] **MAX убыток** показывает значение со знаком, динамическим цветом (красный/зелёный/серый), без `Math.abs` в селекторе и без захардкоженного минуса в JSX. Защита от Infinity. Отдельная `lossExposure` для логики лимита.
- [ ] **Иконка видимости** (Eye/EyeOff) работает в любом режиме, включая зафиксированные позиции. Замочек на этой иконке не показывается. Статус «зафиксирована» — отдельным бейджиком.
- [ ] **Чекбоксы** в таблице сохранений с master-чекбоксом (3 состояния), пакетным удалением через `Promise.allSettled`, одним общим `confirm`, сбросом при смене фильтров.

# Знаки (+/−) в блоке «Базовый актив» — спецификация для нового калькулятора

**Источник:** beta.optioner.online (старый калькулятор, CalculatorV2)
**Дата фиксации поведения:** 2026-04-28
**Передача в:** calc.optioner.online (переписка с нуля)
**Статус в старом проекте:** реализовано и задеплоено в продакшен

---

## 1. Зачем

В карточке «Базовый актив» (рядом с лимитом на инструмент и MAX-убытком) есть три ключевые строки:

1. **Стоимость позиций** — суммарный кеш-флоу по позициям базового актива при входе.
2. **Затраты на опционы и маржин** — кеш-флоу по премиям опционов при входе.
3. **Итого** — итоговый нетто-кеш-флоу всей конструкции при входе.

Раньше все три значения отображались по абсолютной величине, без знака. Это было неинформативно: покупка акций и продажа выглядели одинаково, как и Buy-call и Sell-call, хотя экономически это противоположные операции (одни — затраты, другие — полученный кредит). «Итого» в результате тоже считалось по запутанной ветвящейся формуле и не отражало реальный нетто-кеш-флоу.

Решение: каждая из трёх строк показывает значение **со знаком**, «Итого» — простая арифметическая сумма с учётом знаков.

---

## 2. Семантика знаков

Договорённость с продакт-овнером (фиксируется как часть контракта блока):

| Операция | Знак | Смысл |
|---|---|---|
| LONG-позиция БА (покупка акций / контрактов) | **−** | Затраты — деньги ушли |
| SHORT-позиция БА (продажа без покрытия) | **+** | Получили деньги |
| Buy-опцион (Call или Put) | **−** | Заплатили премию |
| Sell-опцион (Call или Put) | **+** | Получили премию |
| «Итого» | сумма со знаками | Реальный нетто-кеш-флоу при входе в конструкцию |

Знак **относится к денежному потоку клиента в момент открытия позиции**, не к будущему P&L и не к рыночной цене.

---

## 3. Формулы расчёта

Все формулы используют только данные на момент **входа** в позицию (цена входа / премия входа). Текущая рыночная цена в этом блоке не участвует — она используется в живом P&L и в расчёте максимального убытка, это другие метрики.

### 3.1. Стоимость позиций БА

```
positionsCost = Σ ( sign(pos) × |quantity × entryPrice| ) / leverage

где sign(pos) =  −1, если позиция LONG
                +1, если позиция SHORT
    leverage  = плечо для базового актива (см. §3.4), ≥ 1
```

В сумму входят только видимые позиции (учитывается флаг видимости из таблицы позиций). Скрытые/выключенные позиции игнорируются.

Деление на `leverage` отражает маржинальное требование брокера: при покупке/шорте notional делится на плечо (например, при плече 4 — реально блокируется 25% от стоимости акций). LONG и SHORT делятся симметрично. Если `leverage = 1`, формула эквивалентна старой (без плеча).

### 3.2. Премия опционов

```
optionsCost = Σ ( sign(opt) × |quantity| × entryPremium × contractMultiplier )

где sign(opt) =  −1, если действие Buy
                +1, если действие Sell
```

`entryPremium` — цена входа опциона: ASK для Buy, BID для Sell (как уже принято в проекте). `contractMultiplier` — множитель контракта (100 для акций, pointValue для фьючерсов).

В сумму входят только видимые и заполненные опционы (есть дата экспирации, страйк, премия).

> **Важно:** маржинальные требования по шортовым опционам в эту строку **НЕ включаются**, несмотря на слово «маржин» в подписи. Маржа — отдельная метрика, она вычисляется и используется в других местах (расчёт требуемого капитала, проверка покрытий). Если в новом калькуляторе захочется честно включить маржу — это изменение контракта строки, требует отдельного обсуждения.

> **Плечо к опционной премии не применяется.** Премия уплачивается/получается в полном объёме при открытии позиции — это не маржинальная операция в том же смысле, что покупка акций. См. §3.4.

### 3.3. Итого

```
totalCost = positionsCost + optionsCost
```

Без условий, без `Math.max`, без особой обработки нулей. Просто сумма двух чисел со знаками. Поскольку `positionsCost` уже делён на плечо, `totalCost` отражает реальный нетто-кеш-флоу с учётом маржи.

### 3.4. Плечо для базового актива

Глобальная пользовательская настройка калькулятора. Применяется к строке «Стоимость позиций» (§3.1), к «Итого» (§3.3 — автоматически, через positionsCost) и к проверке лимита на инструмент (§4 — через usedCapital).

**Где настраивается:** панель «Настройки» калькулятора, поле «Плечо для базового актива».

**Хранение:** `localStorage`, ключ `baseAssetLeverage`, формат — число.

**Дефолт:** 4.

**Диапазон:** число `>= 1`, шаг 0.5. Дробные значения допускаются (брокеры предлагают плечи 1.5, 3.3 и т.п.).

**Защита от мусора:** при `leverage` = NaN / `< 1` / `undefined` / нечисло — компонент использует 1 (т.е. ведёт себя как до плеча). UI принудительно нормализует ввод к минимуму 1 при потере фокуса.

**Что плечо НЕ делит:**
- Опционную премию (`optionsCost` в §3.2).
- P&L базового актива и P&L TOTAL (это финансовый результат, а не блокированный капитал).
- MAX убыток (та же причина).

**Подпись строки:** при `leverage > 1` подпись становится `Стоимость позиций (плечо N)`; при `leverage = 1` остаётся `Стоимость позиций` как раньше.

**Совместимость с сохранёнными конфигурациями:** плечо НЕ сохраняется внутри сохранённой стратегии. Это глобальная настройка пользователя (зависит от брокерского счёта), а не часть конкретной конструкции опционов. При загрузке любой сохранённой конфигурации плечо берётся из текущего значения в localStorage.

## 4. Лимит на инструмент

Лимит на инструмент (`депозит / количество инструментов`, см. блок «Финансовый контроль») сравнивается с «Итого» по правилу:

```
usedCapital = max(0, −totalCost)        // сколько денег реально вложили
exceeded = (limit > 0) && (usedCapital > limit)
excessAmount = exceeded ? usedCapital − limit : 0
```

Логика:
- Если `totalCost < 0` (нетто-затраты) — сравниваем `|totalCost|` с лимитом.
- Если `totalCost ≥ 0` (нетто-кредит, на счёт пришли деньги) — лимит **никогда не считается превышенным**: вкладывать ничего не пришлось.

Плашка с лимитом отображается в двух состояниях, тексты сохраняются как в старом калькуляторе: «В РАМКАХ ЛИМИТА» / «ПРЕВЫШЕНИЕ на $ X».

## 5. Отображение

### 5.1. Формат числа со знаком

Используем единый формат для всех трёх строк (он же уже применяется к P&L в этой же карточке):

```
+$ 1 234        — для положительных
−$ 1 234        — для отрицательных (минус U+2212, не дефис)
$ 0             — для нуля (без знака)
```

Разделитель тысяч — пробел. Округление до целого доллара.

### 5.2. Цвет

| Строка | Цвет | Палитра нового проекта (ADR-009) |
|---|---|---|
| Стоимость позиций | нейтральный | служебный текстовый цвет |
| Затраты на опционы и маржин | нейтральный | служебный текстовый цвет |
| **Итого** | **зелёный** при `+`, **красный** при `−`, нейтральный при `0` | использовать стандартные «успех/ошибка» из палитры |

Не раскрашивать первые две строки — иначе блок становится пёстрым. В «Итого» цвет уместен, так как это итоговая метрика и пользователь должен сразу понять, кредит у него на руках или затраты.

### 5.3. MAX-убыток — не трогать

В этом же блоке есть строка «MAX убыток». Это отдельная метрика (наихудший сценарий по P&L), всегда отображается со знаком минус и красным цветом. Знаки этой строки не относятся к описываемой задаче.

## 7. Чек-лист переноса в новый калькулятор

- [ ] Функция расчёта лимита использует `usedCapital = max(0, −totalCost)` — отдельный юнит-тест на сценарии 1, 2, 5.
- [ ] Форматтер `formatSignedAmount` (или его аналог) — общий с форматированием P&L; использует Unicode-минус U+2212.
- [ ] В UI: цветной только «Итого», остальные две строки — нейтральные.
- [ ] Маржа шортов в строку «Затраты на опционы и маржин» **не добавляется** (если будет нужно — отдельный ADR в новом проекте).
- [ ] Подпись строки можно пересмотреть: слово «и маржин» в нынешнем тексте формально неверно (маржа не учитывается). В новом проекте можно переименовать, например, в «Премия опционов». Это решение продакт-овнера.
- [ ] Совместимость с расширением Chrome (ADR-013): расширение передаёт `quantity`, `entryPrice`, `action`, `type` в тех же ключах — формулы должны принимать значения как есть, без преобразований знака на стороне расширения.

## 8. Открытые вопросы для нового проекта

1. **Включать ли маржу шортов в строку «Затраты на опционы и маржин»?** В старом калькуляторе функция расчёта требуемого капитала уже существует (учитывает Reg T, покрытые позиции, спреды). Технически вынести её в эту строку — небольшая работа. Но это меняет смысл «Итого» (становится не просто кеш-флоу, а кеш-флоу + блокировка средств). Решение принимает продакт.
2. **Подпись строки 2.** Если маржу не включаем — переименовать в «Премия опционов» (точное название) или оставить «Затраты на опционы» (привычное название из старого UI).
3. **Фьючерсы.** Знаки и формулы те же, разница только в `contractMultiplier` (берётся из `pointValue` инструмента). Стоит явно покрыть фьючерсный кейс юнит-тестом.

# Якорная P&L (Fact P&L) — масштабирование по количеству контрактов

**Источник:** beta.optioner.online (старый калькулятор, CalculatorV2)
**Дата фиксации поведения:** 2026-05-04
**Передача в:** calc.optioner.online (переписка с нуля)
**Статус в старом проекте:** реализовано и задеплоено в продакшен (v38)
**Связанные handoff:** `leverage-base-asset.md`, `signed-amounts-base-asset-block.md`

---

## 1. Зачем

В таблице опционов есть ячейка «Fact P&L» — пользователь вводит в неё **фактическую** прибыль/убыток, которую видит у брокера на конкретный момент. Эта ячейка работает как **якорь**: дальше калькулятор считает теоретическую дельту от якоря (изменение цены актива, дней до экспирации, IV) и прибавляет её к якорному значению. Так пользователь видит проекцию своей реальной P&L в будущее, а не «голую» теоретическую модель.

Выявленный баг: пока ячейка пуста, P&L строки растёт строго пропорционально количеству контрактов. Как только пользователь вводит Fact P&L и затем меняет количество (что-если симуляция «а если бы у меня было N контрактов»), результат становится **непропорциональным** — разница ползёт на десятки и сотни долларов на контракт.

Пример (Buy CALL AMKR strike 85, цена 70.96, Fact P&L = −$228, qty=1 → P&L = −$1858):
| Кол. | Что показывает | Что должно показывать |
|---|---|---|
| 1 | −$1858 | −$1858 |
| 2 | −$3462 | ≈ −$3716 |
| 5 | −$8314 | ≈ −$9290 |

Импакт: непропорциональный P&L просачивался в ИТОГО, MAX убыток, MAX прибыль и точку безубытка — пользователь принимал решения по искажённой картине.

Баг жил в проде с момента появления функции Fact P&L (~26 марта 2026, ~6 недель).

---

## 2. Корень

Якорная формула применялась так:

```
pl_displayed = actualPL + (pl_theoretical_now − pl_theoretical_at_anchor)
```

`pl_theoretical_now` и `pl_theoretical_at_anchor` рассчитывались через `calculateOptionPLValue` / `calculateFuturesOptionPLValue`, которые **уже умножают на quantity**. То есть дельта `(pl − plAtAnchor)` масштабируется текущим количеством — линейно растёт с qty.

А `actualPL` — это «сырая» долларовая константа, введённая пользователем когда-то при количестве `qty_at_anchor`. При изменении qty оно остаётся прежним. Получается смешение масштабов: дельта × N, якорь × 1 → итог не пропорционален N.

---

## 3. Решение

Сохранять количество в момент ввода Fact P&L (новое поле `actualPLQuantity`) и в формуле масштабировать якорь пропорционально:

```
ratio = currentQuantity / actualPLQuantity   (если actualPLQuantity > 0, иначе 1)
pl_displayed = actualPL × ratio + (pl_theoretical_now − pl_theoretical_at_anchor)
```

Семантика: пользователь видит у брокера −$228 при 1 контракте. Если он симулирует «а что если бы у меня было 2 контракта той же позиции» — система показывает −$456 как якорь, дельта тоже масштабируется на 2x, итог пропорционален. При qty без изменений ratio = 1 — поведение совпадает с пользовательским вводом.

---

## 4. Поля модели опциона

| Поле | Тип | Когда заполняется | Когда сбрасывается |
|---|---|---|---|
| `actualPL` | `number \| null` | При вводе Fact P&L | При очистке ячейки |
| `actualPLDate` | `string (ISO YYYY-MM-DD) \| null` | Сегодняшняя дата ввода | При очистке ячейки |
| `actualPLPrice` | `number \| null` | Текущая цена БА из блока «Симуляция» (`targetPrice` или fallback на `currentPrice`) | При очистке ячейки |
| `actualPLQuantity` | `number \| null` | **Текущее `option.quantity` в момент ввода** (новое поле) | При очистке ячейки |

Все четыре поля заполняются и сбрасываются **синхронно** в одном обработчике (`handleActualPLChange` в OptionsTableV3.jsx).

При повторном вводе Fact P&L (обновление существующего якоря) все четыре поля перезаписываются текущими значениями — и `actualPLQuantity` тоже обновляется на текущее количество.

## 5. Формулы

### 5.1. P&L строки таблицы и ИТОГО

```
if (actualPL !== null && actualPLDate && daysPassed >= anchorDaysPassed):
    qtyAnchor   = actualPLQuantity > 0 ? actualPLQuantity : (currentQuantity || 1)
    qtyCurrent  = currentQuantity || 0
    ratio       = qtyAnchor > 0 ? (qtyCurrent / qtyAnchor) : 1
    plDisplayed = actualPL × ratio + (plTheoreticalNow − plTheoreticalAtAnchor)
else:
    plDisplayed = plTheoreticalNow            (стандартный расчёт без якоря)
```

`plTheoreticalNow` и `plTheoreticalAtAnchor` рассчитываются через единую функцию ценообразования с уже применённым `quantity * contractMultiplier` внутри.

### 5.2. План выхода (ExitPlanTable)

В плане выхода каждый шаг закрывает **часть** позиции — `step.quantity`, не полное количество. Поэтому ratio считается от количества шага:

```
qtyAnchor   = actualPLQuantity > 0 ? actualPLQuantity : (option.quantity || 1)
qtyStep     = step.quantity || 0
ratio       = qtyAnchor > 0 ? (qtyStep / qtyAnchor) : 0
plDisplayed = actualPL × ratio + (plTheoreticalNow − plTheoreticalAtAnchor)
```

При этом `plTheoreticalNow` / `plTheoreticalAtAnchor` рассчитываются с уже подставленным `tempOpt.quantity = step.quantity`. Так суммы шагов плана выхода в сумме дают то же, что таблица опционов целиком.

### 5.3. Что НЕ меняется

- Метрики из верхнего блока (BE, MAX убыток, MAX прибыль, Risk/Reward) — считаются через `calculatePLDataForMetrics`, которая якорь **не использует**. Поведение этих метрик не зависит от наличия Fact P&L. Это намеренно — метрики должны отражать чисто-теоретический риск стратегии.
- График P&L — тоже без якоря. Якорь — это «коррекция отображения» в табличных колонках, не модификатор глобальной модели риска.
- Расчёт греков — без якоря.

## 6. Поведение при изменении полей

| Действие пользователя | actualPL | actualPLDate | actualPLPrice | actualPLQuantity |
|---|---|---|---|---|
| Ввод значения в ячейку Fact P&L | новое значение | сегодня (ISO) | текущий targetPrice | текущий option.quantity |
| Очистка ячейки Fact P&L | `null` | `null` | `null` | `null` |
| Изменение количества контрактов в строке | без изменений | без изменений | без изменений | **без изменений** (намеренно) |
| Изменение цены актива в блоке «Симуляция» | без изменений | без изменений | без изменений | без изменений |
| Перезагрузка страницы | восстанавливается из localStorage | восстанавливается | восстанавливается | восстанавливается |

Ключевое решение: **при изменении количества `actualPLQuantity` НЕ обновляется**. Это и есть точка опоры формулы — благодаря старому якорному количеству ratio считается корректно. Если бы оно обновлялось при каждом изменении qty, мы бы потеряли якорь.

Если пользователь хочет «перезаякорить» Fact P&L под новое количество — он перевводит значение в ячейку. Это записывает все четыре поля заново, и `actualPLQuantity` совпадёт с новым количеством.

## 7. Хранение и инициализация

| Параметр | Значение |
|---|---|
| Где хранится | `localStorage` (как часть `userOptionOverridesRef`) |
| Ключи | те же, что для других якорных полей: `actualPL`, `actualPLDate`, `actualPLPrice`, **новое** `actualPLQuantity` |
| Дефолт при отсутствии (старые сохранения) | `null` → формула применяет fallback `actualPLQuantity = currentQuantity` (т.е. ratio = 1) |
| Валидация при чтении | `Number(...) > 0`; иначе fallback |

**Миграция совместимости:** для старых конфигураций, у которых уже сохранены `actualPL/actualPLDate/actualPLPrice` без `actualPLQuantity`, применяется fallback `actualPLQuantity = option.quantity` на момент чтения. Это даёт `ratio = 1` — то есть старое (некорректное) поведение для уже сохранённых якорей. Новые ввoды работают корректно. Без отдельной миграции данных это сознательный компромисс: пользователь может перевводом якоря «обновить» его до правильного поведения.

## 8. Места применения формулы в старом коде

В старом проекте формула якоря дублирована в нескольких местах. В новом проекте лучше вынести в одну утилиту, но для понимания контекста — список всех точек:

| Файл | Что считает | Кол. формул |
|---|---|---|
| `frontend/src/components/CalculatorV2/OptionsTableV3.jsx` | P&L строки, Close Price строки, ИТОГО | 3 |
| `frontend/src/hooks/usePositionExitCalculator.js` | Сценарий 2 и сценарий 3 расчёта позиции выхода | 2 |
| `frontend/src/components/CalculatorV2/CalculatorDealTabs/ExitPlanTable.jsx` | P&L шага плана выхода | 1 |

Все шесть точек используют одну и ту же шаблонную формулу `actualPL × ratio + (pl − plAtAnchor)`. Расчёт `plAtAnchor` идентичен во всех точках:
- Цена БА на момент якоря: `actualPLPrice` (fallback на текущую цену).
- Дни до экспирации на момент якоря: `calculateDaysRemainingUTC(option, anchorDaysPassed, ...)`.
- IV на момент якоря: `manualIvOverride` (если задан) или текущая теоретическая IV.

## 9. UI

### 9.1. Сама ячейка Fact P&L

Ничего не меняется. Это `<input type="number" step="0.01">` в строке таблицы. Подсветка фоном `#fef3c7` пока есть значение, прозрачная пока нет.

### 9.2. Должны ли подсветить «количество в момент якоря»?

В старом проекте — **нет**. Решение: формула масштабирует под капотом, пользователю не показывается ни ratio, ни actualPLQuantity. В будущем (новый проект) можно подумать о тултипе на ячейке: «введено при N контрактов» — но это UX-улучшение, не обязательная часть фикса.

### 9.3. Должна ли ячейка показывать масштабированное значение?

В старом проекте — **нет**. Ячейка показывает то, что пользователь ввёл (`option.actualPL`). Масштабируется только итоговая P&L строки. Это намеренно — иначе пользователь не сможет редактировать своё значение, не вводя его заново.

## 10. Сценарии для тестирования

Для всех сценариев: AMKR, цена 70.96, Buy CALL strike 85, premium ASK ≈ $13.6, expiration 18.12.26, Fact P&L = −$228 при qty=1.

| # | Действия | Ожидаемый результат |
|---|---|---|
| Q1 | Создать опцион, qty=1, не трогать Fact P&L | P&L строки = −$1858 (теоретический). При qty=2 → ≈ −$3716 (×2). При qty=5 → ≈ −$9290 (×5). |
| Q2 | Создать опцион, qty=1, ввести Fact P&L = −228 | P&L строки = −$1858 (якорь применился). |
| Q3 | После Q2: изменить qty на 2 | P&L строки = −$3716 (×2 пропорционально). Fact P&L в ячейке остался −228. |
| Q4 | После Q2: изменить qty на 5 | P&L строки = −$9290 (×5 пропорционально). |
| Q5 | После Q3 (qty=2, P&L=−3716): перевввести Fact P&L = −500 | P&L строки = (−500 × 2/2) + Δ = −500 + Δ. actualPLQuantity обновился на 2. |
| Q6 | После Q5: изменить qty на 4 | P&L строки = (−500 × 4/2) + Δ_qty4 = −1000 + Δ_qty4. |
| Q7 | Очистить Fact P&L (стереть значение) | P&L строки возвращается к чисто-теоретическому расчёту. Все четыре поля обнулены. |
| Q8 | Перезагрузить страницу с заполненным Fact P&L | actualPL/Date/Price/Quantity восстанавливаются из localStorage. P&L строки идентичен тому, что был до перезагрузки. |
| Q9 | Загрузить старую сохранённую конфигурацию без actualPLQuantity | actualPLQuantity = текущее option.quantity (fallback). Ratio = 1, поведение как раньше. |
| Q10 | План выхода: qty=5, Fact P&L=−1140 (= −228×5), шаг закрывает 2 контракта | P&L шага ≈ −456 + (Δ при qty=2). Сумма всех шагов на 100% = −1140 + (Δ при qty=5). |

## 11. Чек-лист переноса в новый калькулятор

- [ ] В модели опциона добавить поле `actualPLQuantity: number \| null`.
- [ ] В обработчике ввода Fact P&L заполнять все четыре поля (`actualPL`, `actualPLDate`, `actualPLPrice`, `actualPLQuantity`) синхронно. При очистке — все четыре в `null`.
- [ ] В обработчике изменения количества контрактов **не** трогать `actualPLQuantity` (оставлять как есть).
- [ ] Вынести якорную формулу в одну утилиту `applyAnchorPL(plRaw, plAtAnchorRaw, opt, currentQty)` или эквивалент. В старом проекте формула продублирована в 6 местах — это технический долг, в новом проекте его сразу не воспроизводить.
- [ ] В плане выхода (ExitPlanTable-аналог) использовать `step.quantity` вместо `option.quantity` при расчёте ratio.
- [ ] Сериализация конфигураций / расширения: `actualPLQuantity` сохраняется и восстанавливается так же, как `actualPL/Date/Price`. Если приходит без него — fallback `option.quantity` (ratio=1).
- [ ] Юнит-тесты на сценарии Q1–Q10.
- [ ] Документация формулы в коде: одна строка комментария «ratio = current/anchor; якорь масштабируется так же, как дельта, иначе непропорциональный P&L» хватит — длинных эссе не нужно.

## 12. Открытые вопросы для нового проекта

1. **Хранить ли `actualPLQuantity` отдельно или внутри объекта якоря?** Семантически это часть якоря наряду с `actualPLDate` и `actualPLPrice`. В новом проекте может быть удобнее сгруппировать в подобъект `option.anchor = { value, date, price, quantity }`, чем держать четыре плоских поля. Это рефакторинг модели, формулы не меняются.
2. **Авто-перезаякоривание при изменении qty.** Сейчас при изменении количества якорь остаётся «зафиксирован» при старом количестве, формула делит/умножает. Альтернатива: при изменении qty автоматически масштабировать `actualPL` и обновить `actualPLQuantity = newQty`. Поведение пользователю невидимо одинаковое, но семантика хранения другая. Решение продакта.
3. **Тултип «введено при N контрактов».** Если новый UI хочет показать пользователю, что Fact P&L был зафиксирован при определённом qty (для прозрачности расчёта), достаточно добавить тултип на ячейку. Технически данные есть.
4. **Метрики верхнего блока (BE, MAX) с учётом якоря.** Сейчас они якорь не используют — это сознательное решение. Если в новом проекте захотим показать BE «с учётом моей реальной позиции» — это отдельная фича со своей формулой и UI-указателем «реальный BE» vs «теоретический BE». Сейчас вне scope.
5. **Якорь для портфеля (multi-leg).** Сейчас якорь — на отдельный опцион. Если пользователь зафиксировал Fact P&L для всей конструкции (например, спред = $X), это не моделируется. Можно добавить «якорь портфеля» как отдельную сущность. Сейчас вне scope.

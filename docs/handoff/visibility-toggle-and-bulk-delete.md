# Handoff: иконка видимости в любом режиме + пакетное удаление сохранений

**Источник:** beta.optioner.online (старый калькулятор, CalculatorV2)
**Назначение:** calc.optioner.online (переписка с нуля)
**Актуально на:** 2026-05-06

---

## 1. Зачем

Это два UX-решения, не математика. Объединены в один документ, потому что оба про управление состоянием в UI и оба родились из одной обратной связи: «не блокируйте мне действия, которые я хочу совершить».

### 1.1. Иконка видимости

В таблице опционов и в строках базового актива каждая запись имеет иконку слева — глазок (Eye) для видимой записи и зачёркнутый глазок (EyeOff) для временно скрытой. Клик по иконке исключает строку из расчётов калькулятора и метрик, не удаляя её. Это стандартный приём для «что-если»-анализа: пользователь хочет посмотреть, как изменится P&L и риск, если убрать одну ногу стратегии.

**Проблема:** для **зафиксированных позиций** (`isLockedPosition === true`, у позиций, загруженных из сохранения и помеченных как реально открытые) иконка превращалась в красный замочек (Lock) и переставала кликаться. Семантика была: «эта позиция реальна, её нельзя скрыть/изменить». На практике это блокировало основной аналитический сценарий: пользователь хотел временно посмотреть, что будет без одной ноги — но не мог, потому что замочек.

### 1.2. Пакетное удаление сохранений

Страница со списком сохранённых конфигураций показывает таблицу со столбцами «Дата», «Тикер», «Тип», «Статус», «Название», «Автор», «Действия». В колонке «Действия» — кнопки «Редактировать» и «Удалить», работающие построчно. Также есть кнопки «Удалить всё» (всю БД) и «Сбросить» (фильтры).

**Проблема:** пользователю нужно удалить N конфигураций по выбору — например, 5 мусорных черновиков, оставив остальные. Старый UI требовал нажимать «Удалить» для каждой и подтверждать каждое удаление через `window.confirm`. Это N×(клик + диалог + клик), для 10 записей — 30 действий.

---

## 2. Решение

### 2.1. Иконка видимости — всегда Eye/EyeOff

Иконка замочка убрана полностью — никогда не показывается, ни в таблице опционов, ни в блоке базового актива. Всегда рендерится пара Eye/EyeOff с работающим обработчиком `toggleVisibility(id)`. Зафиксирована позиция или нет — на иконку видимости это не влияет.

Семантическое обоснование: статус «зафиксирована» уже виден в шапке позиции (бейджик «🔒 Зафиксирована»), дублировать его на каждой строке таблицы не имело смысла. Видимость и зафиксированность — независимые атрибуты, и их наложение через одну иконку путает пользователя больше, чем помогает.

**Что не меняется:** `isLockedPosition` остаётся как флаг для блокировки **редактирования** числовых полей (количество, премия, страйк, дата) — это правильное поведение, не позволяющее случайно поправить параметры реально открытой позиции. Только иконка видимости теперь работает всегда.

### 2.2. Чекбоксы + кнопка пакетного удаления

В таблице сохранений добавлена первая колонка с чекбоксом. Шапка таблицы — master-чекбокс с тремя состояниями:

| Состояние master-чекбокса | Условие |
|---|---|
| `unchecked` | ни одна запись текущей страницы не выделена |
| `checked` | все записи текущей страницы выделены |
| `indeterminate` (квадратик-минус) | выделена часть |

Клик по master-чекбоксу: если `checked` или `indeterminate` — снимает выделение со всех записей текущей страницы; иначе — добавляет все записи текущей страницы в выделение. Записи, скрытые фильтрами или находящиеся на других страницах пагинации, master-чекбоксом не затрагиваются.

Кнопка «Удалить выбранные (N)» появляется в шапке страницы рядом с «Удалить всё» — становится активной, как только выделена хотя бы одна запись. Её действие:

1. Один общий `window.confirm` — «Удалить N конфигураций?». Не N подтверждений.
2. Параллельные DELETE-запросы через `Promise.allSettled` — один сбой не блокирует остальные.
3. Сводный отчёт: «Удалено: M. Не удалось удалить: K» (только если K > 0).
4. После завершения — `setSelectedIds(new Set())` и перезагрузка списка.

**Сброс выделения:**

- При смене любого фильтра (дата, тикер, автор, тип, статус) выделение сбрасывается — иначе пользователь рискует случайно удалить записи, которые скрыты текущим фильтром.
- При смене страницы пагинации выделение **сохраняется** — пользователь может пройти по 5 страницам, выделяя по 2 записи на каждой, и одной кнопкой удалить все 10.

### 2.3. Право на удаление

В старом проекте была политика «удалять можно только свои конфигурации» (проверка `author === currentUserName` во фронте). На текущем этапе пользователь явно попросил снять это ограничение — выделять и удалять можно любые записи; авторизация остаётся за backend (если он откажет, фронт покажет «Не удалось удалить: K»).

**Для нового проекта это решение продакта:** хотите ли вы политику «только свои» во фронте, или полагаетесь только на серверную авторизацию. Технически в коде должен быть один параметр `userId` (или эквивалент), передаваемый в DELETE; backend сам решает, имеет ли пользователь право.

## 3. Замечания по реализации

### 3.1. Native checkbox vs UI-обёртка

В старом проекте использован нативный `<input type="checkbox">` с tailwind-классами (`accent-cyan-500`, размеры через `h-4 w-4`), а не радиксовая обёртка `<Checkbox>` из `components/ui/`. Причина — обёртка была написана как `.tsx` с алиасом `@/lib/utils`, который CRA-сборка проекта не разрешает (модуль не находился в build). Нативный input работает везде.

В новом проекте, если есть нормальная UI-библиотека с правильной сборкой, лучше использовать обёртку — она доступнее (focus ring, индикатор фокуса, ARIA), но математика поведения та же.

### 3.2. Indeterminate через ref

У нативного `<input type="checkbox">` нельзя задать `indeterminate` через атрибут — только через `element.indeterminate = true`. В React это делается через `ref={el => { if (el) el.indeterminate = ... }}`. Не самый красивый паттерн, но рабочий.

### 3.3. Производительность

Множество выделенных ID хранится как `Set<id>`, обновляется иммутабельно (`new Set(prev); next.add(id)`). При типичном размере 50 записей на странице это бесплатно. Если в новом проекте будет много записей (тысячи), стоит предусмотреть виртуализацию таблицы и проверить, что master-чекбокс работает корректно с виртуальными строками.

## 5. Чек-лист переноса в новый калькулятор

### Видимость

- [ ] У каждой строки опциона и базового актива иконка видимости — Eye/EyeOff, **независимо** от `isLockedPosition` или аналогичного флага.
- [ ] Клик по иконке всегда вызывает `toggleVisibility(id)`. Никакой `disabled` логики.
- [ ] Замочек и любая «индикация заблокированности» на самой иконке видимости — не нужны. Статус позиции показывается отдельно (например, бейджик в шапке строки).
- [ ] `isLockedPosition` остаётся как флаг для блокировки редактирования полей, но не для иконки видимости.

### Пакетное удаление

- [ ] Колонка с чекбоксом в таблице сохранений — первая.
- [ ] Master-чекбокс в шапке поддерживает три состояния: `checked`, `indeterminate`, `unchecked`. Логика клика — переключает по правилу из §2.2.
- [ ] Master-чекбокс работает только по записям **текущей страницы пагинации**, не по всему отфильтрованному списку и не по всей БД.
- [ ] Состояние выделения хранится как `Set<id>`. Иммутабельные обновления.
- [ ] Сброс выделения при смене любого фильтра. Сохранение выделения при смене страницы пагинации.
- [ ] Кнопка «Удалить выбранные (N)»: активна при `selectedIds.size > 0`, рядом с «Удалить всё».
- [ ] Удаление через `Promise.allSettled` (а не `Promise.all`) — один сбой не блокирует остальные.
- [ ] Один общий `confirm` перед удалением, не N подтверждений.
- [ ] Сводный отчёт об ошибках только когда `failed > 0`. Молчаливый успех если всё удалилось.
- [ ] После удаления — `setSelectedIds(new Set())` + перезагрузка списка.

## 6. Открытые вопросы для нового проекта

1. **Политика «только свои».** В текущей версии фронт разрешает удалять любые записи, авторизацию оставляем серверу. Нужно ли вернуть фронтовую политику «только свои» для предотвращения случайных удалений чужого пользователем-админом? Решение продакта.
2. **Master-чекбокс по всему отфильтрованному списку.** Сейчас он работает только по текущей странице. Если у пользователя 200 записей и он хочет выделить ВСЕ отфильтрованные — нужен отдельный механизм («выделить все 187» после выделения страницы), как в Gmail. В старом проекте этого нет; для нового — это UX-фича уровня middle-priority.
3. **Анимация перехода при удалении.** Сейчас удалённые записи просто исчезают после reload. Можно добавить fade-out перед перезагрузкой — чисто косметика, без функционального эффекта.
4. **Индикатор прогресса при пакетном удалении.** При удалении N записей фронт ставит `loading=true`, но не показывает «Удалено M из N». Если N большое — стоит добавить прогресс. Сейчас вне scope.

# Спецификация: перенос данных crypto с Supabase на собственную базу (путь Б)

**Дата:** 2026-06-10
**Статус:** утверждён дизайн, ожидает плана реализации
**Контекст:** crypto.optioner.online хранит состояние в облаке Supabase. Supabase периодически
ставит бесплатный проект на паузу, из-за чего хост перестаёт резолвиться и (через захардкоженный
upstream в nginx) роняет ВЕСЬ веб-сервер вместе с beta. Цель — убрать зависимость от Supabase,
перенеся хранение в инфраструктуру, которой мы управляем.

---

## 1. Цель и критерии приёмки

**Цель:** crypto работает без Supabase — данные хранятся в базе beta, доступ закрыт паролем,
существующие данные перенесены без потерь.

**Критерии приёмки:**
1. crypto.optioner.online открывается; при отсутствии «пропуска» показывает экран ввода пароля.
2. С верным паролем приложение загружает данные из нашей базы и сохраняет изменения в неё.
3. С неверным паролем (или без него) данные нельзя ни прочитать, ни записать — проверяет сервер.
4. Существующие данные из Supabase (`app_state`, id='global') скопированы в новую таблицу.
5. В коде crypto не осталось обращений к Supabase; пакет `@supabase/supabase-js` удалён.
6. nginx-конфиг crypto больше не содержит upstream на `*.supabase.co` — соответственно, пауза
   Supabase физически не может больше уронить веб-сервер.
7. Поведение для пользователя не меняется: мгновенная работа из оффлайн-кэша, фоновая синхронизация,
   защита от затирания пустыми данными сохранены.

## 2. Текущее состояние (что реально используется в Supabase)

Аудит кода `crypto/src` показал минимальное использование:
- **Одна таблица `app_state`**, одна строка `id='global'`, поле `content` — весь стейт приложения
  как единый JSON-документ (финансы, недельная статистика, настройки, активы). Поле `updated_at`.
- **Операции:** только `select content where id='global'` (single) и `upsert {id, content, updated_at}`.
- **Supabase Auth — фактически НЕ используется**: в коде нет вызовов `signIn/signUp/getSession` и т.п.;
  данные общие (один глобальный документ), не привязаны к пользователям. `auth.ts` — UI-обвязка без
  реальных вызовов аутентификации.
- **НЕ используются:** realtime, storage, RPC, edge functions, RLS-логика.
- Клиент ходит на `${origin}/sb` (nginx-прокси) с anon-ключом.

Вывод: фактическая потребность — «прочитать/сохранить один JSON-документ по HTTP с защитой доступа».

## 3. Целевая архитектура

### 3.1 Хранилище (база beta)
- Новая таблица `crypto_app_state` в базе beta (PostgreSQL прод / SQLite локально), через существующий
  механизм `backend/app/database.py` (SQLAlchemy `Base`, `SessionLocal`, `create_all`).
- Колонки: `id` (TEXT, PK, значение `'global'`), `content` (JSON), `updated_at` (timestamp).
- Одна строка. Модель — отдельный файл в `backend/app/models/`.

### 3.2 Серверный блок (backend beta)
Новый изолированный роутер `backend/app/routers/crypto_state.py`, подключается в `app/main.py`
через `include_router`. Три обработчика под префиксом (через nginx будет доступен как `/api/...`
на домене crypto):

1. **POST `/crypto/login`** — принимает пароль. Сверяет с хэшем пароля из переменной окружения
   `CRYPTO_APP_PASSWORD_HASH`. При успехе выдаёт подписанный токен-пропуск (HMAC-подпись секретом
   `CRYPTO_TOKEN_SECRET`, со сроком жизни, напр. 90 дней). При неуспехе — 401.
   Защита от перебора: ограничение частоты попыток (rate-limit), напр. задержка/лимит на IP.
2. **GET `/crypto/state`** — требует валидный токен-пропуск (заголовок). Возвращает `content`
   строки `id='global'` (или пустой/дефолтный, если строки ещё нет). Без токена — 401.
3. **PUT `/crypto/state`** — требует валидный токен-пропуск. Делает upsert `{id:'global', content,
   updated_at}`. Без токена — 401.

Проверка токена — общая зависимость (dependency) роутера. Пароль и секрет — только из окружения,
в коде/гите их нет.

### 3.3 nginx (vhost crypto.optioner.online)
- Удалить блок `location /sb/` (проксирование на Supabase) — источник падений.
- Добавить `location /api/` → проксирование на backend beta `http://127.0.0.1:8002/crypto/`
  (оба vhost на одном сервере). CORS не нужен — тот же домен.

### 3.4 Фронтенд crypto
- `crypto/src/lib/supabase.ts` — удалить (или заменить тонким HTTP-клиентом к `/api`).
- `crypto/src/Store.ts` — два метода работы с облаком (`loadFromCloud`, `saveToCloud`) переписать
  с вызовов supabase-js на `fetch()`:
  - чтение: `GET /api/state` с заголовком пропуска;
  - запись: `PUT /api/state` с заголовком пропуска и телом = стейт.
  Оффлайн-кэш в localStorage и «защита от затирания пустыми данными» — сохранить как есть.
- Экран пароля: при старте, если в браузере нет валидного пропуска — показать поле ввода пароля,
  по сабмиту вызвать `POST /api/login`, сохранить полученный пропуск в localStorage, затем грузить
  данные. `auth.ts` (Supabase-обвязка) заменить на этот простой парольный экран.
- Убрать зависимость `@supabase/supabase-js` из `crypto/package.json`.
- Переменные `VITE_SUPABASE_URL` / `VITE_SUPABASE_ANON_KEY` больше не нужны (секрета во фронте нет —
  пароль вводит пользователь). Базовый адрес API — относительный `/api`.

### 3.5 Локальная разработка
- Vite dev-прокси для `/api` → локальный backend beta (`http://127.0.0.1:8002`) вместо текущего
  прокси на Supabase. Данные в dev — локальная SQLite базы beta.

## 4. Перенос существующих данных (миграция)
Пока Supabase снова доступен — **до переключения** один раз скопировать актуальный документ:
1. Прочитать `content` строки `id='global'` из Supabase (anon-ключ ещё валиден).
2. Записать его в новую таблицу `crypto_app_state` (id='global') в базе beta (прод).
3. Сверить, что данные на месте, и только потом переключать nginx/фронт.
Разовый скрипт; в гит секреты не коммитим.

## 5. Конфигурация и секреты
- **Backend beta env** (не в гите; добавить в `.env.*.template` как пустые образцы):
  - `CRYPTO_APP_PASSWORD_HASH` — хэш выбранного пароля.
  - `CRYPTO_TOKEN_SECRET` — секрет для подписи пропусков (случайная строка).
- Пароль выбирает владелец (сгенерирован надёжный вариант); хранится у владельца и на сервере —
  только как хэш.

## 6. Обработка ошибок
- Неверный пароль → понятное сообщение, повтор; rate-limit от перебора.
- Истёк/невалиден пропуск → возврат к экрану пароля.
- Backend/сеть недоступны → приложение продолжает работать из localStorage-кэша (текущее поведение),
  синхронизация возобновляется при восстановлении связи.
- Сохранение: «защита от потери» (пустое не затирает непустое облако) остаётся.
- try-catch вокруг всех сетевых вызовов с понятными сообщениями (правило проекта).

## 7. Тестирование
- **Backend (pytest):** логин с верным/неверным паролем; get/put стейта с валидным/невалидным/
  отсутствующим токеном; upsert создаёт и обновляет одну строку.
- **Фронт:** ручная проверка — экран пароля, загрузка, сохранение, перезагрузка страницы (пропуск
  помнится), оффлайн-режим.
- **Приёмка на проде:** crypto открывается, данные на месте (после миграции), сохранение работает,
  beta не затронут, пауза Supabase больше ни на что не влияет.

## 8. Порядок выкатки
1. Backend: таблица + роутер + env на сервере (`pm2 restart` optioner-backend-beta).
2. Миграция данных из Supabase в новую таблицу (прод).
3. Фронт crypto: сборка с новым клиентом + парольным экраном → деплой в `/var/www/crypto`.
4. nginx crypto: убрать `/sb/`, добавить `/api/` → reload (с разрешения владельца — прод).
5. Проверка по критериям приёмки. Откат: вернуть прежний nginx-конфиг/сборку (бэкап).

## 9. Вне области (YAGNI)
- Многопользовательская регистрация/аккаунты (данные общие, один пароль).
- Realtime, файловое хранилище, сложные таблицы/связи.
- Перенос на платный Supabase (это альтернатива пути Б, не делаем).

## 10. Затрагиваемые компоненты
- `backend/app/models/` — новая модель таблицы.
- `backend/app/routers/crypto_state.py` — новый роутер; `app/main.py` — подключение.
- `backend/app/database.py` — использование существующего механизма (создание таблицы).
- nginx vhost `crypto.optioner.online` (на сервере) — отдельный шаг с разрешением.
- `crypto/src/Store.ts`, `crypto/src/auth.ts`, `crypto/src/lib/supabase.ts`, `crypto/package.json`,
  `crypto/vite.config.ts`.
- Разовый скрипт миграции данных.

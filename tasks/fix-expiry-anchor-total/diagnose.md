# Диагноз: ИТОГО без защиты якоря на экспирации

## Root cause

Файл `frontend/src/components/CalculatorV2/OptionsTableV3.jsx` реализует логику
«якоря Fact P&L» (пользователь может вручную зафиксировать реальную P&L опциона —
`actualPL` — на определённую дату `actualPLDate`; дальнейшая P&L проецируется как
`P&L = actualPL * anchorRatio + (текущая теоретическая P&L − теоретическая P&L на
дату якоря)`). Эта логика продублирована в компоненте (и в одном utils-файле) в
4 независимых местах:

1. Блок суммирования ИТОГО (`useMemo` для `optionsTableTotalPL`, ~строки 180-249) —
   **без защиты**.
2. Расчёт P&L отдельной строки таблицы (~строка 1320) — с защитой
   `optionDaysRemaining > 0 && ...`.
3. Расчёт P&L для колонки «Close» (~строка 1535) — с защитой
   `optionDaysRemaining > 0 && ...`.
4. `frontend/src/utils/startPLSnapshot.js` (~строка 202) — с защитой.

## Почему это баг

Защита `optDaysRemaining > 0` физически означает: «на дату экспирации (дней до
экспирации ≤ 0) якорь не применяется, P&L считается чистой формулой
`intrinsic_value − премия`». Это необходимо, потому что теоретическая цена опциона
на экспирации не зависит от волатильности (time value = 0, T=0 в BSM) — но
теоретическая P&L НА ДАТУ ЯКОРЯ (`plAtAnchor`) считается при ненулевом времени до
экспирации, с волатильностью на тот момент (в т.ч. `manualIvOverride`, он же
«Fact IV»). Если якорь всё равно применяется на экспирации, разница
`(pl − plAtAnchor)` может быть сколь угодно большой (в частности, при высоком Fact
IV на дату якоря), и итоговая P&L перестаёт быть ограничена суммой уплаченных
премий (максимальный убыток купленной позиции).

Поскольку блок ИТОГО (единственный без защиты) считает P&L каждой опционной ноги
самостоятельно, а не суммирует уже отображённые в строках значения — баг проявлялся
только в итоговой сумме, а строки таблицы (которые используют защищённую формулу)
показывали корректные значения. Отсюда несовпадение «итог ≠ сумма строк».

## Репро (прод)

Сделка `dbConfig=2a797da0-fba4-4332-bbb5-cb95fd482f23` (тикер MKTX):
- 4 CALL 130 @ 3.97 (куплено)
- 2 PUT 115 @ 8.02 (куплено)
- Суммарная премия: $3192 (= 4×3.97×100 + 2×8.02×100)

Шаги:
1. Открыть сделку, выставить ползунок дней = 72 (дата экспирации).
2. Ввести Fact IV пута = 100%.

Ожидаемо: строки корректны (−1588 / −1604, что и есть чистая P&L на экспирации при
цене актива между страйками — обе ноги истекают без внутренней стоимости).
Фактически (до фикса): ИТОГО показывало −$4210 — по модулю больше суммы премий
($3192), что невозможно для купленной (long) позиции.

## Scope фикса

Изменена только защита в блоке суммирования ИТОГО (OptionsTableV3.jsx, ~строка 220):
добавлено условие `optDaysRemaining > 0` перед применением якорной поправки —
по образцу уже существующей защиты в блоке расчёта P&L строки (~строка 1320).
Остальные 3 места (расчёт строки, колонка Close, startPLSnapshot.js) уже были
защищены и не менялись. Рефакторинг (вынос общей функции якоря) не выполнялся —
явно исключён из задачи.

## Тест

`frontend/src/utils/__tests__/expiryAnchorInvariant.test.js` — числовой тест,
моделирующий формулу якоря (с защитой и без) поверх реальной функции
`calculateOptionPLValue` (тот же BSM-движок, что использует компонент), на данных
MKTX-репро. Проверяет:
(а) с защитой ИТОГО на экспирации = сумме строк = −премии;
(б) инвариант `|ИТОГО| <= премия` держится с защитой и нарушается без неё —
воспроизводя сам механизм прод-бага.

Полный рендер-тест OptionsTableV3 не делался — компонент требует большого объёма
пропсов/контекста (ivSurface, calculatorMode, стейт таблицы и т.д.), что сделало бы
тест непропорционально тяжёлым по сравнению с точечным численным инвариантом.
